# Benchmarks

Numbers are recorded per iteration on the dev machine (go1.26, linux/amd64,
24 logical CPUs). Reproduce with `make bench`. These are baselines, not promises:
the point is to catch regressions and to show the effect of each iteration.

## Iteration 1 — skeleton (JSON transport)

Iteration 1 uses a temporary JSON codec, so the encode/decode paths allocate.
This is deliberate: the figures below are the **before** picture that the binary
codec in iteration 3 is measured against. The simulation hot path is already
allocation-free.

### Simulation (zero-alloc hot path)

| Benchmark               | ns/op | B/op | allocs/op |
|-------------------------|------:|-----:|----------:|
| Tick / 50 entities      |   875 |    0 |         0 |
| Tick / 200 entities     |  3397 |    0 |         0 |
| AppendEntities / 200    |  3991 |    0 |         0 |

A 200-entity tick costs ~3.4 µs of pure simulation, far under the 33 ms tick
budget — headroom the later networking work will spend.

### Codec (JSON — to be replaced in iteration 3)

| Benchmark                    | ns/op | B/op  | allocs/op |
|------------------------------|------:|------:|----------:|
| EncodeSnapshot / 50 entities |  6963 |  3075 |         1 |
| EncodeSnapshot / 200 entities| 26222 | 12300 |         1 |
| DecodeInput                  |   781 |   544 |        12 |

### Bytes per tick per client (JSON, full-state broadcast)

| Entities in snapshot | Bytes | Bytes/entity |
|----------------------|------:|-------------:|
| 1                    |   105 |        105.0 |
| 8                    |   546 |         68.2 |
| 32                   |  2081 |         65.0 |
| 64                   |  4129 |         64.5 |

At 30 snapshots/s a 64-player room pushes ~124 KB/s **to each client** with the
JSON codec and full-state broadcast. The two levers that bring this down come
later: the binary codec (iteration 3, target ~13 bytes/entity) and interest
management + deltas (iteration 6, so traffic stops scaling with room size).

## Итерация 2 — интерполяция

Симуляция и кодек не менялись, поэтому цифры аллокаций те же, что в итерации 1.
Изменилась частота снапшотов: сервер шлёт **20 Гц** вместо тикрейта 30 Гц
(делитель частоты по Брезенхэму, 2 снапшота на 3 тика). Замер на живом сервере:
**20.4 снапшота/с** при 30.0 тика/с (отношение 0.68 ≈ 2/3).

### Трафик на клиента (JSON, 20 Гц вместо 30 Гц)

Снижение частоты снапшотов на 1/3 напрямую срезает исходящий трафик на 1/3, а
клиентская интерполяция скрывает разрыв — движение остаётся плавным.

| Игроков | Байт/снапшот | Итер. 1 @30 Гц | Итер. 2 @20 Гц | Экономия |
|---------|-------------:|---------------:|---------------:|---------:|
| 8       |          546 |     ~16.4 КБ/с |     ~10.9 КБ/с |     −33% |
| 32      |         2081 |     ~62.4 КБ/с |     ~41.6 КБ/с |     −33% |
| 64      |         4129 |    ~123.9 КБ/с |     ~82.6 КБ/с |     −33% |

Дальнейшее снижение трафика — в итерации 3 (бинарный кодек, ~13 байт/сущность
вместо ~64) и итерации 6 (interest management + дельты).

## Итерация 3 — бинарный протокол

JSON заменён на бинарный кодек (little-endian). Горячие пути стали zero-alloc, а
трафик упал в ~5 раз.

### Кодек: JSON (итер. 1) → бинарный (итер. 3)

| Benchmark                     | Было (JSON)         | Стало (бинарный)   |
|-------------------------------|--------------------:|-------------------:|
| EncodeSnapshot / 50 сущностей | 6963 ns · 1 alloc   | **311 ns · 0 alloc** |
| EncodeSnapshot / 200          | 26222 ns · 1 alloc  | **1237 ns · 0 alloc** |
| DecodeInput                   | 781 ns · 12 alloc   | **1.1 ns · 0 alloc** |

Цель итерации 3 достигнута: `BenchmarkEncodeSnapshot` и `BenchmarkDecodeInput` —
**0 allocs/op**.

### Байт/тик на клиента: JSON → бинарный

Раскладка снапшота: заголовок 10 байт (1 тип + 4 tick + 4 lastProcessedSeq +
1 count) + 12 байт на сущность (2 id + 1 kind + 2 x + 2 y + 2 vx + 2 vy + 1 hp).

| Игроков | JSON, байт | Бинарный, байт | Меньше | Бинарный @20 Гц |
|---------|-----------:|---------------:|-------:|----------------:|
| 1       |        105 |             22 |  −79%  |      ~0.4 КБ/с   |
| 8       |        546 |            106 |  −81%  |      ~2.1 КБ/с   |
| 32      |       2081 |            394 |  −81%  |      ~7.9 КБ/с   |
| 64      |       4129 |            778 |  −81%  |     ~15.2 КБ/с   |

Для 64 игроков связка «20 Гц + бинарный кодек» даёт **~15 КБ/с** на клиента
против ~124 КБ/с у JSON@30 Гц из итерации 1 — в 8 раз меньше. `FuzzDecode`:
28M+ прогонов без паник. Дальше трафик режет только interest management + дельты
(итерация 6).

### Цели дальше

- **Итерация 3 — сделано:** `BenchmarkEncodeSnapshot` и `BenchmarkDecodeInput` =
  0 allocs/op; 12 байт/сущность + 10 байт заголовок.
- **Итерация 6:** tick p99 < 15 мс на 200 ботах; трафик на клиента не растёт
  линейно с числом игроков в комнате (interest management + дельты). Тогда же —
  пул буферов снапшотов на стороне комнаты (сейчас буфер новый на клиента).

## Итерация 4 — предсказание и реконсиляция

Клиент предсказывает своего игрока (`web/game.js`), а сервер получил **очередь
вводов**: `World.Step` осушает накопившиеся за тик вводы (клиент 60 Гц / тик 30 Гц
≈ 2 на тик) и применяет каждый шагом `inputDt = 1/60`. Так сервер потребляет ровно
тот же поток, что переигрывает клиент, — реконсиляция сходится точно, а не «в
среднем». Формат провода и кодек не менялись; `lastProcessedSeq` слался пер-клиент
ещё с итерации 1, лишней полосы реконсиляция не требует.

### Стоимость тика (очередь вводов, ~2 ввода/игрока/тик)

| Benchmark            | ns/op | B/op | allocs/op |
|----------------------|------:|-----:|----------:|
| Tick / 50 сущностей  |  4343 |    0 |         0 |
| Tick / 200 сущностей | 17566 |    0 |         0 |
| AppendEntities / 200 |  6396 |    0 |         0 |

Число выросло против итерации 1 (875 / 3397 ns) намеренно: тик теперь и принимает
вводы (append в переиспользуемую очередь), и применяет по ~2 шага движения на
игрока вместо одного — это уже не «чистый шаг», а полный приём+симуляция. Главное
сохранено: **0 allocs/op** (очередь `Player.inputs` осушается в `[:0]` и
переиспользуется). 17.6 мкс на 200 игроков — 0.05% бюджета тика 33 мс; запас на
итерацию 6 (p99 < 15 мс на 200 ботах) не тронут.

Приёмка — детерминизмом, а не числом: `TestPredictionMatchesAuthoritative`,
`TestReconciliationMatchesAuthoritative` и `TestStepDrainsAllQueuedInputs`
(`internal/game/prediction_test.go`) доказывают, что клиентская модель (свёртка
общего `Step` шагом `inputDt`) байт-в-байт совпадает с авторитетным прогоном для
любой точки частичного подтверждения и что сервер применяет ВСЕ вводы за тик.
Ручная проверка отклика при 200 мс RTT — в браузере (throttling devtools).

## Итерация 5 — бой и lag compensation

Добавлены снаряды, урон, смерть/респаун, reliable-события и **lag compensation**
(сервер перематывает цели к тому, что видел стрелок). Горячий путь остался
zero-alloc: id снарядов проверяются сканом слайса (без map), очереди снарядов и
событий переиспользуются, а история позиций — фиксированный массив `posHist` в
каждом игроке (запись каждый тик без аллокаций).

### Стоимость тика

| Benchmark              | ns/op  | B/op | allocs/op |
|------------------------|-------:|-----:|----------:|
| Tick / 50 (движение)   |   4317 |    0 |         0 |
| Tick / 200 (движение)  |  17693 |    0 |         0 |
| CombatTick / 50 (бой)  | 132060 |    0 |         0 |
| AppendEntities / 200   |   4187 |    0 |         0 |

`BenchmarkCombatTick` — 50 игроков стреляют каждый тик, ~128 снарядов в воздухе,
свит-коллизия каждого против каждого живого игрока (уже с перемоткой цели по
истории): ~132 мкс/тик (0.4% бюджета 33 мс), **0 allocs/op**. Запись истории
позиций идёт в каждом тике (и в «движение», и в «бой») — это присвоение в
фиксированный массив, аллокаций не добавляет. Профиль коллизии — O(снаряды ×
игроки), кандидат на широкофазную оптимизацию в итерации 6 (та же пространственная
сетка, что нужна interest management).

### Lag compensation: цена на проводе

Поле `viewTick` (uint32) удлинило `MsgInput` с 8 до **12 байт** на проводе. Это
восходящий трафик клиент→сервер на 60 Гц: +4 байта × 60 = **+240 Б/с на клиента**
— на фоне снапшотов (нисходящие ~15 КБ/с на 64 игроках) незаметно. Память сервера:
кольцо `posHist` — `historyLen`(32) × 8 байт = 256 байт на игрока (~16 КБ на
комнату из 64), тоже пренебрежимо. Перемотка — чтение одного слота истории по
маске, без аллокаций и без обхода.

### Размеры reliable-сообщений на проводе

| Сообщение  | Байт | Раскладка                                    |
|------------|-----:|----------------------------------------------|
| `MsgSpawn` |    7 | 1 тип + 2 id + 2 x + 2 y                      |
| `MsgDeath` |    5 | 1 тип + 2 victim + 2 killer                   |
| `MsgHit`   |    7 | 1 тип + 2 attacker + 2 victim + 1 dmg + 1 hp  |

Они редки (событие боя, а не поток), поэтому на трафик почти не влияют: доминируют
снапшоты (снаряды в них — те же 12 байт/сущность, что игроки). Сценарий
`join → move → shoot → death → respawn` проходит по сети (`TestE2ECombatKillsAndRespawns`,
`make integration`).

## Итерация 6A — interest management (AOI)

Комната шлёт каждому клиенту только сущности в коробке `±AOIRadius` вокруг его
игрока (сетка `aoiGrid`, клетка 256 юнитов). Это снимает главную статью трафика:
раньше снапшот нёс **всю** комнату, теперь — лишь окрестность зрителя.

### Модель трафика: полный бродкаст vs AOI

Байт/снапшот на клиента = 10 (заголовок) + 12 × сущностей. При полном бродкасте
число сущностей = населению комнаты; при AOI — плотности вокруг зрителя (потолок —
сколько игроков влезает в коробку `2·AOIRadius`), и от размера комнаты уже **не
зависит**.

| Игроков в комнате | Полный бродкаст, байт | AOI (≈16 в виде), байт |
|-------------------|----------------------:|-----------------------:|
| 16                |                   202 |                    202 |
| 64                |                   778 |                   ~202 |
| 200               |                  2410 |                   ~202 |

Пока населения меньше вида — AOI не отсекает ничего (коробка накрывает всех), и
трафик совпадает с полным. Выигрыш включается, когда комната больше вида: при
200 игроках полный бродкаст — ~2.4 КБ/снапшот (×20 Гц = ~48 КБ/с на клиента),
AOI держит клиента на десятках сущностей независимо от того, 200 в комнате или
1000. Это и есть цель итерации 6 — трафик на клиента не растёт линейно с комнатой.

Число сущностей в отправленном снапшоте наблюдаемо через метрику
`arena_entities_per_snapshot`. Замеры под живой нагрузкой (200 ботов, tick p99) —
в разделе итерации 6C вместе с `cmd/loadtest`. Горячий путь (tick, encode, decode)
не тронут: AOI живёт только на пути рассылки, вне бенчей zero-alloc.

## Итерация 6B — дельта-кодирование снапшотов

AOI срезал число сущностей на клиента; дельты срезают байты на сущность. Снапшот
уходит дельтой против подтверждённой клиентом базы: только изменившиеся на проводе
сущности + список ушедших id.

### Overhead провода

| Поле                 | Было | Стало | Δ        |
|----------------------|-----:|------:|---------:|
| `MsgInput` (тело)    |   11 |    15 | +4 (ackTick) |
| `MsgSnapshot` (загол.)|  10 |    14 | +4 (baseTick) + 1 (removedCount) на хвост |

`ackTick` добавляет 4 байта × 60 Гц = **+240 Б/с восходящих** на клиента (как и
`viewTick`, незаметно). Заголовок снапшота вырос на 4 байта плюс 1 байт на хвост
removed — ничтожно на фоне экономии.

### Модель экономии

Полный снапшот вида из N сущностей = 14 + 12·N + 1 байт. Дельта того же вида =
14 + 12·C + 1 + 2·R, где C — изменившиеся сущности, R — ушедшие. Пример: игрок
стоит, вокруг 20 сущностей, из них двигаются 8 → дельта несёт 8 вместо 20:
`14 + 96 + 1 = 111` байт против `14 + 240 + 1 = 255` — **−56%**. Неподвижные
сущности (прицеливающиеся игроки, зависшие снаряды) в дельту не попадают вовсе;
`kind` и обычно `hp` тоже не меняются, но при движении сущность всё равно уходит
целиком (12 байт) — поле-level дельта не делалась (диминишинг, сложность зеркала).

Худший случай — смена почти всего вида (респаун/телепорт: много ушедших + много
новых): дельта была бы крупнее полного, поэтому сервер в этом случае шлёт полный
(`baseTick = 0`). Так дельта никогда не хуже полного.

Экономия наблюдаема по `arena_snapshot_bytes_total` (падают байты при неизменном
`arena_entities_per_snapshot`). Горячий путь остался zero-alloc: `EncodeSnapshot`
50/200 сущностей — **0 allocs/op** (312 ns / 1280 ns), `DecodeInput` — **0 allocs**.
Живые числа под нагрузкой 200 ботов — в разделе 6C.

## Итерация 6C — нагрузка 200 ботов

`cmd/loadtest` поднимает одну комнату на 200 ботов in-process (через
`transport.Pipe`) и меряет, как сервер держит нагрузку. Боты подключаются не по
сети намеренно: tick p99 — это работа горутины комнаты (drain → Step → broadcast →
encode), сокет в неё не входит, поэтому Pipe даёт ту же тик-стоимость без сетевого
джиттера и портов, in-process и воспроизводимо (детерминированный автопилот на
seed). Комната на реальных часах 30 Гц, боты шлют ввод 60 Гц.

### Результат: 200 ботов, одна комната, AOI 640, 30 с

Прогон `make loadtest` (go1.26, linux/amd64, 24 CPU; сервер и боты в одном
процессе):

| Метрика                     | Значение              |
|-----------------------------|-----------------------|
| длительность тика           | p50 1.3 мс · **p99 2.5 мс** · max 2.9 мс |
| бюджет тика / цель           | 33 мс / p99 < 15 мс — **пройдено с запасом ~6×** |
| сущностей в снапшоте         | avg 26.6 · max 55 (в комнате 200!) |
| трафик на клиента (снапшоты) | ~7.2 КБ/с |
| dropped inputs               | 0 |

Итог итерации 6 виден в двух числах: **сущностей в снапшоте ~27, а не 200** —
interest management держит клиента на его окрестности независимо от размера
комнаты; **трафик ~7 КБ/с против ~48 КБ/с** у полного бродкаста 200 игроков
(`14 + 200·12` байт × 20 Гц) — **−85%** за счёт AOI (основное) и дельт (тонкая
подрезка: под постоянным движением большинство из ~27 видимых сущностей меняются,
поэтому дельта срезает немного — её выигрыш растёт с долей неподвижных). tick p99
на 200 ботах — **2.5 мс**, в 6 раз под целью, так что запас на рост есть.

### Пул буферов снапшотов

Раньше каждый снапшот на клиента кодировался в свежий буфер (`AppendSnapshot(nil,
…)`): при 200 клиентах × 20 Гц это ~4000 буферов/с мусора на комнату плюс
перерасту́ты `append`. Итерация 6C переиспользует буферы через `sync.Pool` (`*[]byte`,
чтобы Put не боксил заголовок среза): комната берёт буфер в `sendSnapshot`, write
pump возвращает его после записи (транспорт данные копирует), выброшенные из
очереди — тоже возвращаются. A/B на одном seed (RNG-поток ботов один и тот же;
тайминг по реальным часам, поэтому аллокации близки, а не идентичны — разницу
доминирует пул):

| Прогон (10 с)     | аллокаций | циклов GC | tick p99 |
|-------------------|----------:|----------:|---------:|
| без пула          |   870 395 |         8 |  2.96 мс |
| с пулом           |   599 607 |         6 |  2.13 мс |
| **разница**       | **−31 %** |   **−25 %** | **−0.8 мс** |

Экономия больше одного буфера на снапшот: пул убирает и промежуточные
перерасту́ты `append` (буфер приходит уже с ёмкостью). Горячий путь кодека остаётся
zero-alloc; пул снимает аллокации именно на пути рассылки, вне бенчей кодека.

## Итерация 8 — широкофазная коллизия по сетке

Коллизия снаряд×игрок была O(снаряды×игроки): каждый снаряд линейно обходил всех
живых игроков. Итерация 8 строит детерминированную сим-сетку живых игроков
(`hitGrid`, клетка 256, геометрия общая с AOI) и запрашивает только клетки вокруг
сегмента снаряда — O(снаряды×кандидаты).

Тонкость lag comp: широкая фаза строится по позициям, но попадание проверяется по
**перемотанной** цели. Чтобы совпадение с брутфорсом было безусловным (а не
держалось на допущении о макс. скорости), игрок вставляется во все клетки,
пересекающие AABB его позиций за окно перемотки (`rewindAABB` — текущая позиция +
кольцо истории за `[1, maxRewindTicks]`). Это ровно множество, что читает
`targetPos`, поэтому запросу достаточно расшириться лишь на радиус коллизии, и ни
одно возможное попадание не теряется независимо от скорости движения.

### Стоимость фазового прохода (128 снарядов в гуще целей)

Прогон `go test -bench=ProjectileHit -benchmem` (go1.26, linux/amd64, 24 CPU).
Меряется один проход коллизии по всем снарядам; для грида в проход входит
построение сетки. Оба пути zero-alloc (прямые вызовы держат `&pr` на стеке).

| Игроков | Брутфорс   | Широкая фаза | Ускорение |
|--------:|-----------:|-------------:|----------:|
| 50      | 124 201 ns | **3 944 ns** | **~31×**  |
| 200     | 513 784 ns | **13 607 ns**| **~38×**  |

Выигрыш растёт с числом игроков: брутфорс линеен по ним, сетка — по локальной
плотности. `BenchmarkTick`/`BenchmarkCombatTick` остались 0 allocs/op — сетка
живёт во `World` (клетки и буфер кандидатов переиспользуются), горячий путь тика
не аллоцирует.

### Корректность

`TestBroadPhaseAgreesWithBruteforce` сверяет исход широкой фазы с эталонным
брутфорсом на 300 случайных сценах × 50 выстрелов: текущая позиция и история
рассинхронизированы нарочно (перемотанная цель уходит на произвольную дистанцию),
`w.Tick` случаен. Победитель выбирается явным минимумом id среди попавших —
надмножество кандидатов и дубли из соседних клеток безвредны. Сетка в `Checksum`
не входит (производный индекс уже-хешируемых позиций), поэтому детерминизм
симуляции не затронут.

## Итерация 9 — field-level дельта

Дельта итерации 6B слала изменившуюся сущность целиком — фиксированной 12-байтной
записью, даже если сдвинулась только координата. Итерация 9 шлёт в дельте
(`baseTick != 0`) лишь реально изменившиеся **поля** под 1-байтной маской:
`[2B id][1B маска][помеченные поля kind1/x2/y2/vx2/vy2/hp1]`. Маска считается по
**квантованному** представлению (`EntityFieldMask`), так что субквантовое дрожание
дельту не раздувает. Полный снапшот (`baseTick == 0`) остался 12-байтным — без
регресса на старте, когда базы ещё нет.

### Трафик на клиента (loadtest, 200 ботов, 20 с, seed 1)

Честный A/B на одной машине (`git stash` старой полной записи против field-level):

| Сценарий               | Полная запись | Field-level | Экономия |
|------------------------|--------------:|------------:|---------:|
| AOI 640 (реалистичный) |    7.7 КБ/с   |  7.5 КБ/с   |   ~3 %   |
| AOI 0 (полный бродкаст)|   69.0 КБ/с   |  62.9 КБ/с  |   ~9 %   |

ROI скромный — и это ожидаемо: в шутере **всё движется**, поэтому x/y (доминирующие
байты записи) меняются каждый тик и не экономятся. Field-level срезает поля, что
меняются редко: `kind` (никогда после спавна), `hp` (только на попадании), `vx/vy`
(только при смене направления). Под активным автопилотом боты правят скорость почти
каждый тик, так что типичная экономия — ~1 байт (`kind`) на запись.

При AOI 640 выигрыш ещё меньше (~3 %): interest-management churn гонит сущности
в/из коробки зрения, а **новая** сущность в дельте идёт под `FieldAll` = 13B — на
1 байт *больше* полной 12B. Эти +1B на входящих частично съедают экономию на
остающихся. Всплеск новых, впрочем, обычно идёт в паре со всплеском `removed`
(старая база уходит из вида), и тогда порог `changed+removed < view` сам выбирает
полный снапшот. Тик p99 остался ~3 мс (бюджет 33 мс), дропов 0.

### Корректность

Round-trip покрыт с двух сторон: `TestDeltaPropertyRoundTrip` (2000 случайных дельт
со случайными масками, absent-поля нулевые, `encode→decode` тождественно) и
`FuzzDecode` (сид дельты с сущностью; декодер не паникует, успешный decode переживает
re-encode). End-to-end через реальный кодек комнаты — `TestDeltaReconstructionStaysConsistent`:
неизменные `Kind`/`HP` движущегося игрока обязаны пережить дельту (ловит затирание
absent-полей). Наложение полей по маске идентично во всех трёх реконструкторах:
браузер (`web/game.js` `applyDelta`), бот (`internal/bot` `reconstructor`), тест
(`deltaClient`). Дельта — чисто транспортное представление, `Checksum` симуляции не
затрагивает.

## Итерация 11 — транспорт WebRTC DataChannel

Итерация 11 — про транспорт, не про горячий путь. Игровой кодек, шаг тика и снапшоты
не тронуты: те же бинарные кадры теперь идут и по WebRTC DataChannel. Поэтому новых
микробенчей нет — `BenchmarkEncodeSnapshot`/`Tick`/`CombatTick` без изменений (0
allocs/op, см. выше), а стоимость самого DataChannel (DTLS/SCTP по UDP) — это сеть, а
не работа горутины комнаты, которую меряет harness.

Проверка транспорта — функциональная, под тегом integration:

- `TestWebRTCLoopbackRoundTrip` (`internal/transport`) — `AcceptWebRTC` ↔ `DialWebRTC`
  через реальный ICE/DTLS/SCTP (host-кандидаты, localhost): round-trip в обе стороны,
  `Close` будит висящий `Read` с `ErrClosed`.
- `TestE2EWebRTCMovement` (`cmd/server`) — бот подключается по `/rtc` (сигналинг →
  DataChannel), двигается вправо и видит рост своего X: весь стек нового транспорта +
  общий session-путь, тот же, что у WebSocket.

DataChannel "game" — ordered+reliable (дефолт pion), семантически как WebSocket,
поэтому reliable-события и дельта-базы с ack работают без изменений в игровом коде.
Замер задержки/джиттера WebRTC vs WS — за рамками harness (это сетевая метрика);
качественно на localhost разницы для геймплея нет.

## Итерация 12 — WebRTC до продакшена (TURN + unreliable снапшоты)

Тоже транспортная итерация: игровой кодек, шаг тика и снапшоты не тронуты (провод —
те же байты, меняется лишь по какому каналу и с какой надёжностью они идут). Горячий
путь без регресса, всё 0 allocs/op (go1.26, 24 CPU, `-benchmem`, `-run=^$`):

```
BenchmarkEncodeSnapshot/50ent-24         321.9 ns/op    0 B/op   0 allocs/op
BenchmarkEncodeSnapshot/200ent-24        1260   ns/op    0 B/op   0 allocs/op
BenchmarkEncodeSnapshotDelta/50ent-24    332.9 ns/op    0 B/op   0 allocs/op
BenchmarkEncodeSnapshotDelta/200ent-24   1282   ns/op    0 B/op   0 allocs/op
BenchmarkDecodeInput-24                    7.075 ns/op    0 B/op   0 allocs/op
BenchmarkTick/50ent-24                    7516   ns/op    0 B/op   0 allocs/op
BenchmarkTick/200ent-24                  32159   ns/op    0 B/op   0 allocs/op
BenchmarkCombatTick-24                   10415   ns/op    0 B/op   0 allocs/op
```

Роутинг снапшота в `Session` — одна function-value индиректность (`sendSnapshot`,
выбранная один раз в `newSession`), на горячий путь не влияет.

Смысл изменения — не пропускная способность, а **задержка при потере пакета**. На
одном reliable+ordered SCTP-канале один потерянный UDP-датаграм держит head-of-line
blocking: все следующие снапшоты ждут его ретрансмита. Отдельный unreliable+unordered
канал "state" (`MaxRetransmits=0`) убирает это — новый снапшот приходит сразу, а
устаревший потерянный не переигрывается (он и не нужен). Эту разницу видно только под
реальной потерей на сети — harness (loopback, без потерь) её не воспроизводит, поэтому
числом её здесь нет; проверка — функциональная.

Проверка транспорта (integration):

- `TestWebRTCUnreliableDelivers` (`internal/transport`) — сервер шлёт снапшот через
  `UnreliableWriter` (канал "state"), клиент читает его тем же `Read`: второй канал
  поднят и подключён к `recv`.
- `TestWebRTCTURNRelay` (`internal/transport`) — in-process TURN-сервер (`pion/turn`,
  статические креды) + `ForceRelay`: DataChannel открывается **только** через relay
  (host/srflx отброшены) и гоняет данные в обе стороны — TURN-путь работает от конфига
  до канала.
- `TestSnapshotRoutedUnreliably` / `TestSnapshotFallsBackToReliable` (`internal/game`) —
  снапшот идёт `WriteUnreliable`, когда транспорт умеет, иначе обычным `Write` (WS/Pipe,
  без регресса).
- `TestICEServersFromEnv` (`cmd/server`) — сборка STUN/TURN из env (креды у TURN).
- `TestE2EWebRTCMovement` (`cmd/server`) — прежний e2e теперь неявно гоняет снапшоты по
  unreliable-каналу через реальный сервер.

## Итерация 14B — persister (комната → канал → БД)

Итерация про архитектуру персиста, не про горячий путь. Запись в БД вынесена в отдельную
горутину персистера (`internal/persist`), к горутине комнаты не приближается. Отправка из
комнаты — неблокирующий `select`/`default` (`Room.sendPersist`): при переполнении канала
сообщение роняется (счётчик + warn-once), тик НИКОГДА не блокируется на store I/O. Эмит
идёт по событиям (смерть, конец матча), не поллингом.

Инвариант zero-alloc горячего пути держится (не тронут):

- `BenchmarkEncodeSnapshot` — 0 B/op, 0 allocs/op (50 и 200 сущностей).
- `BenchmarkDecodeInput` — 0 allocs/op.

Провод: `Join` получил `Token` (`[2B tokenLen][token]`), но Join — рукопожатие (один раз
на соединение), не горячий путь; декод токена аллоцирует строку только на рукопожатии.
`persistMatchResult` аллоцирует свежий срез участников — но это переход бой→антракт (раз в
~3 минуты на комнату), вне тик-цикла. `persistKill` (частый) буфер не аллоцирует — читает
`AccountID` с игроков и шлёт значение в канал.

Функциональная проверка вместо чисел:

- `internal/persist` — live kills/deaths по смертям, суицид/окружение (только death), отсев
  гостей (`AccountID 0`), пропуск матча без зарегистрированных участников; games/wins + история
  на итог матча (`RecordMatch` не задваивает kills/deaths). На in-memory SQLite.
- `internal/game` — `persistKill`/`persistMatchResult` шлют корректные события; nil-sink —
  no-op; переполненный канал роняет и считает дроп, не блокируясь.
- `cmd/server` — `resolveIdentity`: валидный токен привязывает аккаунт и берёт имя из токена
  (анти-имперсонация), пустой/битый — гость; e2e (боты-гости) через новый формат Join.
