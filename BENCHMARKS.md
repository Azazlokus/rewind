# Benchmarks

Numbers are recorded per iteration on the dev machine (go1.26, linux/amd64,
24 logical CPUs). Reproduce with `make bench`. These are baselines, not promises:
the point is to catch regressions and to show the effect of each iteration.

## Iteration 1 — skeleton (JSON transport)

Iteration 1 uses a temporary JSON codec, so the encode/decode paths allocate.
This is deliberate: the figures below are the **before** picture that the binary
codec in iteration 3 is measured against. The simulation hot path is already
allocation-free.

### Simulation (zero-alloc hot path)

| Benchmark               | ns/op | B/op | allocs/op |
|-------------------------|------:|-----:|----------:|
| Tick / 50 entities      |   875 |    0 |         0 |
| Tick / 200 entities     |  3397 |    0 |         0 |
| AppendEntities / 200    |  3991 |    0 |         0 |

A 200-entity tick costs ~3.4 µs of pure simulation, far under the 33 ms tick
budget — headroom the later networking work will spend.

### Codec (JSON — to be replaced in iteration 3)

| Benchmark                    | ns/op | B/op  | allocs/op |
|------------------------------|------:|------:|----------:|
| EncodeSnapshot / 50 entities |  6963 |  3075 |         1 |
| EncodeSnapshot / 200 entities| 26222 | 12300 |         1 |
| DecodeInput                  |   781 |   544 |        12 |

### Bytes per tick per client (JSON, full-state broadcast)

| Entities in snapshot | Bytes | Bytes/entity |
|----------------------|------:|-------------:|
| 1                    |   105 |        105.0 |
| 8                    |   546 |         68.2 |
| 32                   |  2081 |         65.0 |
| 64                   |  4129 |         64.5 |

At 30 snapshots/s a 64-player room pushes ~124 KB/s **to each client** with the
JSON codec and full-state broadcast. The two levers that bring this down come
later: the binary codec (iteration 3, target ~13 bytes/entity) and interest
management + deltas (iteration 6, so traffic stops scaling with room size).

## Итерация 2 — интерполяция

Симуляция и кодек не менялись, поэтому цифры аллокаций те же, что в итерации 1.
Изменилась частота снапшотов: сервер шлёт **20 Гц** вместо тикрейта 30 Гц
(делитель частоты по Брезенхэму, 2 снапшота на 3 тика). Замер на живом сервере:
**20.4 снапшота/с** при 30.0 тика/с (отношение 0.68 ≈ 2/3).

### Трафик на клиента (JSON, 20 Гц вместо 30 Гц)

Снижение частоты снапшотов на 1/3 напрямую срезает исходящий трафик на 1/3, а
клиентская интерполяция скрывает разрыв — движение остаётся плавным.

| Игроков | Байт/снапшот | Итер. 1 @30 Гц | Итер. 2 @20 Гц | Экономия |
|---------|-------------:|---------------:|---------------:|---------:|
| 8       |          546 |     ~16.4 КБ/с |     ~10.9 КБ/с |     −33% |
| 32      |         2081 |     ~62.4 КБ/с |     ~41.6 КБ/с |     −33% |
| 64      |         4129 |    ~123.9 КБ/с |     ~82.6 КБ/с |     −33% |

Дальнейшее снижение трафика — в итерации 3 (бинарный кодек, ~13 байт/сущность
вместо ~64) и итерации 6 (interest management + дельты).

## Итерация 3 — бинарный протокол

JSON заменён на бинарный кодек (little-endian). Горячие пути стали zero-alloc, а
трафик упал в ~5 раз.

### Кодек: JSON (итер. 1) → бинарный (итер. 3)

| Benchmark                     | Было (JSON)         | Стало (бинарный)   |
|-------------------------------|--------------------:|-------------------:|
| EncodeSnapshot / 50 сущностей | 6963 ns · 1 alloc   | **311 ns · 0 alloc** |
| EncodeSnapshot / 200          | 26222 ns · 1 alloc  | **1237 ns · 0 alloc** |
| DecodeInput                   | 781 ns · 12 alloc   | **1.1 ns · 0 alloc** |

Цель итерации 3 достигнута: `BenchmarkEncodeSnapshot` и `BenchmarkDecodeInput` —
**0 allocs/op**.

### Байт/тик на клиента: JSON → бинарный

Раскладка снапшота: заголовок 10 байт (1 тип + 4 tick + 4 lastProcessedSeq +
1 count) + 12 байт на сущность (2 id + 1 kind + 2 x + 2 y + 2 vx + 2 vy + 1 hp).

| Игроков | JSON, байт | Бинарный, байт | Меньше | Бинарный @20 Гц |
|---------|-----------:|---------------:|-------:|----------------:|
| 1       |        105 |             22 |  −79%  |      ~0.4 КБ/с   |
| 8       |        546 |            106 |  −81%  |      ~2.1 КБ/с   |
| 32      |       2081 |            394 |  −81%  |      ~7.9 КБ/с   |
| 64      |       4129 |            778 |  −81%  |     ~15.2 КБ/с   |

Для 64 игроков связка «20 Гц + бинарный кодек» даёт **~15 КБ/с** на клиента
против ~124 КБ/с у JSON@30 Гц из итерации 1 — в 8 раз меньше. `FuzzDecode`:
28M+ прогонов без паник. Дальше трафик режет только interest management + дельты
(итерация 6).

### Цели дальше

- **Итерация 3 — сделано:** `BenchmarkEncodeSnapshot` и `BenchmarkDecodeInput` =
  0 allocs/op; 12 байт/сущность + 10 байт заголовок.
- **Итерация 6:** tick p99 < 15 мс на 200 ботах; трафик на клиента не растёт
  линейно с числом игроков в комнате (interest management + дельты). Тогда же —
  пул буферов снапшотов на стороне комнаты (сейчас буфер новый на клиента).

## Итерация 4 — предсказание и реконсиляция

Клиент предсказывает своего игрока (`web/game.js`), а сервер получил **очередь
вводов**: `World.Step` осушает накопившиеся за тик вводы (клиент 60 Гц / тик 30 Гц
≈ 2 на тик) и применяет каждый шагом `inputDt = 1/60`. Так сервер потребляет ровно
тот же поток, что переигрывает клиент, — реконсиляция сходится точно, а не «в
среднем». Формат провода и кодек не менялись; `lastProcessedSeq` слался пер-клиент
ещё с итерации 1, лишней полосы реконсиляция не требует.

### Стоимость тика (очередь вводов, ~2 ввода/игрока/тик)

| Benchmark            | ns/op | B/op | allocs/op |
|----------------------|------:|-----:|----------:|
| Tick / 50 сущностей  |  4343 |    0 |         0 |
| Tick / 200 сущностей | 17566 |    0 |         0 |
| AppendEntities / 200 |  6396 |    0 |         0 |

Число выросло против итерации 1 (875 / 3397 ns) намеренно: тик теперь и принимает
вводы (append в переиспользуемую очередь), и применяет по ~2 шага движения на
игрока вместо одного — это уже не «чистый шаг», а полный приём+симуляция. Главное
сохранено: **0 allocs/op** (очередь `Player.inputs` осушается в `[:0]` и
переиспользуется). 17.6 мкс на 200 игроков — 0.05% бюджета тика 33 мс; запас на
итерацию 6 (p99 < 15 мс на 200 ботах) не тронут.

Приёмка — детерминизмом, а не числом: `TestPredictionMatchesAuthoritative`,
`TestReconciliationMatchesAuthoritative` и `TestStepDrainsAllQueuedInputs`
(`internal/game/prediction_test.go`) доказывают, что клиентская модель (свёртка
общего `Step` шагом `inputDt`) байт-в-байт совпадает с авторитетным прогоном для
любой точки частичного подтверждения и что сервер применяет ВСЕ вводы за тик.
Ручная проверка отклика при 200 мс RTT — в браузере (throttling devtools).

## Итерация 5 — бой и lag compensation

Добавлены снаряды, урон, смерть/респаун, reliable-события и **lag compensation**
(сервер перематывает цели к тому, что видел стрелок). Горячий путь остался
zero-alloc: id снарядов проверяются сканом слайса (без map), очереди снарядов и
событий переиспользуются, а история позиций — фиксированный массив `posHist` в
каждом игроке (запись каждый тик без аллокаций).

### Стоимость тика

| Benchmark              | ns/op  | B/op | allocs/op |
|------------------------|-------:|-----:|----------:|
| Tick / 50 (движение)   |   4317 |    0 |         0 |
| Tick / 200 (движение)  |  17693 |    0 |         0 |
| CombatTick / 50 (бой)  | 132060 |    0 |         0 |
| AppendEntities / 200   |   4187 |    0 |         0 |

`BenchmarkCombatTick` — 50 игроков стреляют каждый тик, ~128 снарядов в воздухе,
свит-коллизия каждого против каждого живого игрока (уже с перемоткой цели по
истории): ~132 мкс/тик (0.4% бюджета 33 мс), **0 allocs/op**. Запись истории
позиций идёт в каждом тике (и в «движение», и в «бой») — это присвоение в
фиксированный массив, аллокаций не добавляет. Профиль коллизии — O(снаряды ×
игроки), кандидат на широкофазную оптимизацию в итерации 6 (та же пространственная
сетка, что нужна interest management).

### Lag compensation: цена на проводе

Поле `viewTick` (uint32) удлинило `MsgInput` с 8 до **12 байт** на проводе. Это
восходящий трафик клиент→сервер на 60 Гц: +4 байта × 60 = **+240 Б/с на клиента**
— на фоне снапшотов (нисходящие ~15 КБ/с на 64 игроках) незаметно. Память сервера:
кольцо `posHist` — `historyLen`(32) × 8 байт = 256 байт на игрока (~16 КБ на
комнату из 64), тоже пренебрежимо. Перемотка — чтение одного слота истории по
маске, без аллокаций и без обхода.

### Размеры reliable-сообщений на проводе

| Сообщение  | Байт | Раскладка                                    |
|------------|-----:|----------------------------------------------|
| `MsgSpawn` |    7 | 1 тип + 2 id + 2 x + 2 y                      |
| `MsgDeath` |    5 | 1 тип + 2 victim + 2 killer                   |
| `MsgHit`   |    7 | 1 тип + 2 attacker + 2 victim + 1 dmg + 1 hp  |

Они редки (событие боя, а не поток), поэтому на трафик почти не влияют: доминируют
снапшоты (снаряды в них — те же 12 байт/сущность, что игроки). Сценарий
`join → move → shoot → death → respawn` проходит по сети (`TestE2ECombatKillsAndRespawns`,
`make integration`).
