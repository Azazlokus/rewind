# Протокол (v1)

Все сообщения — little-endian, первый байт — тип сообщения. Пакет
`internal/protocol` содержит типы и кодек и не зависит ни от игры, ни от сети.

> **Статус кодека.** С итерации 3 кодек **бинарный** (little-endian), как описано
> ниже; временный JSON итерации 1 удалён. Типы и публичные функции (`Append*`,
> `Decode*`) переезд не заметили — менялась только кодировка. Квантование позиций
> и скоростей вынесено в `quantize.go`.

> **Транспорт.** Эти кадры транспортно-независимы: одни и те же байты идут и по
> WebSocket (`/ws`), и по WebRTC DataChannel (итерация 11, `?transport=webrtc`).
> С итерации 12 у WebRTC **два** DataChannel: "game" (ordered+reliable) несёт JoinAck,
> Spawn/Death/Hit и вводы, "state" (unordered+unreliable) — снапшоты (потеря допустима,
> зато нет head-of-line blocking). Байты сообщений при этом те же; на приёме их
> различают по типу, а не по каналу. Сигналинг WebRTC (config/offer/answer, JSON по WS
> `/rtc`; в `config` — ICE-серверы с TURN-кредами и флаг relay-only) — установление
> соединения, а не игровой протокол; он описан в [architecture.md](architecture.md).

## Требования к кодеку

1. **Никогда не паниковать** на мусорном/обрезанном вводе — только ошибки.
   Гарантируется фаззингом (`FuzzDecode`).
2. **Round-trip без потерь**: `encode → decode` возвращает исходное значение.
   Property-тест на случайных сообщениях.
3. **Zero-alloc encode** при переиспользуемом буфере (цель итерации 3;
   бенчмарк `BenchmarkEncodeSnapshot` должен показывать 0 allocs/op).

## Клиент → сервер

### MsgInput (0x01)

Формат на проводе:

```
[1B type][4B seq uint32][1B buttons][2B aim uint16][4B viewTick uint32][4B ackTick uint32][1B actions?]
```

- **seq** — порядковый номер ввода (клиент шлёт 60 Гц). Сервер складывает вводы в
  очередь игрока и за тик применяет все накопившиеся по одному (шагом `1/InputRate`),
  двигая `lastProcessedSeq`; по нему клиент отбрасывает подтверждённые вводы при
  reconciliation.
- **buttons** — битовая маска: бит 0..3 = WASD (`Up/Left/Down/Right`), бит 4 = fire,
  биты 5..7 = выбор оружия (итер. 26): 3-битное поле, 0 = «не менять», 1..4 = выбрать
  оружие (`WeaponSelect = (buttons >> 5) & 7`).
- **actions** — опциональный завершающий байт (итер. 27): биты действий/абилок, не
  влезших в занятый `buttons`. Бит 0 = `ActDash` (рывок). Старый ввод без этого байта
  декодируется с `actions = 0` (обратная совместимость; боты/e2e не ломаются). Сервер
  гейтит рывок по своему кулдауну — доверять клиенту частоту нельзя (анти-чит).
- **aim** — угол прицеливания, `0..65535` отображается на `0..2π`.
- **viewTick** — серверный тик, к которому клиент интерполировал в момент этого
  ввода (что игрок реально видел на экране). Сервер использует его для **lag
  compensation**: перематывает цели к позиции на этом тике, зажимая перемотку в
  окно `maxRewindTicks` (анти-чит). `0` означает «клиент ещё не получал снапшотов»
  — тогда сервер стреляет по настоящему. Клиент считает его как
  `serverTime × tickRate`, зеркаля семантику `Snapshot.tick`.
- **ackTick** — метка последнего снапшота, который клиент полностью получил и
  реконструировал. Сервер кодирует следующий снапшот **дельтой** против него (см.
  ниже). `0` — «ещё ничего не подтверждено», тогда сервер шлёт полный снапшот.

### MsgJoin (0x02)

```
[1B type][1B nameLen][name UTF-8, max 16B][2B tokenLen][token UTF-8, max 512B][1B spectator?]
```

Имя валидируется: не длиннее 16 байт и корректный UTF-8. `token` (итерация 14B) —
подписанный токен-сессия из бэкенда (`/api/register`, `/api/login`, `/api/guest`);
`tokenLen 0` — аноним. Шлюз проверяет токен: валидный — привязывает сессию к аккаунту
и берёт **имя из токена** (клиент не может назваться чужим именем через поле `name`);
пустой/битый/просроченный — деградация до гостя (`accountID 0`) с именем из `name`.

`spectator` (итерация 22) — **опциональный** завершающий байт: `1` — клиент хочет
наблюдать без спавна (не создаётся `Player`, не участвует в бою). Байт отсутствует или
`0` — обычный игрок; старый формат без байта декодируется как игрок. Наблюдателю
`MsgJoinAck` несёт `YourID == 0` (сигнал «своей сущности нет»); он получает снапшоты
(весь мир, вне AOI) и reliable-события, но в симуляцию не входит и ввод не подаёт.

## Сервер → клиент

### MsgSnapshot (0x10)

```
[1B type][4B tick][4B baseTick][4B lastProcessedSeq][1B changedCount]
  затем changedCount × запись сущности (раскладка зависит от baseTick):
    полный (baseTick == 0): [2B id][1B kind][2B x][2B y][2B vx][2B vy][1B hp]  (12B)
    дельта (baseTick != 0): [2B id][1B маска][только помеченные поля в порядке
                            kind(1B)/x(2B)/y(2B)/vx(2B)/vy(2B)/hp(1B)]
[1B removedCount] затем removedCount × [2B id]
```

- **baseTick** — метка снапшота-базы. `0` — **полный** снапшот: `changed` несёт весь
  набор фиксированными 12-байтными записями, `removed` пуст. Иначе — **дельта**
  против снапшота с меткой `baseTick`, где каждая изменённая запись несёт только
  поля из маски (см. «Дельта-кодирование» и «Field-level дельта»).
- **lastProcessedSeq** — **своё для каждого получателя**: номер последнего ввода
  этого клиента, применённого сервером. На нём строится клиентская реконсиляция.
- **changed** — новые/изменённые сущности; **removed** — id тех, кто был в базе и
  пропал (у полного снапшота — 0).
- **координаты квантуются**: карта 4096×4096, шаг 1/16 юнита (`CoordScale`).
- **changedCount/removedCount** — по одному байту, поэтому в снапшоте не больше 255
  сущностей каждого рода (`MaxEntities`).

#### Дельта-кодирование (итерация 6B)

Клиент подтверждает в каждом `Input` метку последнего реконструированного снапшота
(`ackTick`). Сервер держит на каждую сессию кольцо недавно отправленных наборов
сущностей и кодирует следующий снапшот **дельтой** против подтверждённой базы:
только изменившиеся на проводе сущности (сравнение по квантованным полям,
`EntityFieldMask`) плюс список ушедших id. Если подтверждённая база выпала из
кольца (клиент сильно отстал/большой RTT) или дельта не короче полного — шлётся
полный снапшот (`baseTick = 0`).

Реконструкция полного набора из базы и дельты — на получателе: **remove**, затем
**changed** поверх копии базы. Так делают все три стороны одинаково: сервер
(база = что он отправил), браузерный клиент (`web/game.js`, `applyDelta`) и
headless-бот (`internal/bot`, `reconstructor`). Инвариант: клиент подтверждает
только тик, который держит у себя, поэтому база дельты всегда есть. Дельты — поверх
interest management: вместе они держат трафик на клиента не зависящим от размера
комнаты (см. `BENCHMARKS.md`).

#### Field-level дельта (итерация 9)

В дельте (`baseTick != 0`) изменившаяся сущность несёт не всю 12-байтную запись, а
только реально изменившиеся **поля** под битовой маской:

```
[2B id][1B маска] затем помеченные поля в фиксированном порядке
маска: FieldKind(1) FieldX(2) FieldY(4) FieldVX(8) FieldVY(16) FieldHP(32)
поле присутствует ⇔ его бит взведён; размеры kind1/x2/y2/vx2/vy2/hp1
```

- Маску считает `protocol.EntityFieldMask` по **квантованному** представлению
  (`internal/game`, `diffEntities`): поле помечено, только если изменилось на проводе,
  так что субквантовое дрожание не раздувает дельту.
- **Новая** (отсутствующая в базе) сущность идёт под `FieldAll` (все шесть битов) —
  фактически те же данные, что и полная запись, плюс байт маски.
- Получатель накладывает присутствующие поля поверх копии сущности из базы;
  отсутствующие берутся из базы без изменений. `id` на проводе есть всегда и в маску
  не входит. Неизвестные биты маски декодер отбрасывает (`& FieldAll`).
- Полный снапшот (`baseTick == 0`) маску **не** использует — там всегда 12-байтные
  записи (без регресса на старте, когда базы ещё нет).
- Константы маски зеркалит `web/game.js` (`PROTO.Field*`); все три реконструктора
  (клиент, бот, тест-`deltaClient`) накладывают поля одинаково.

### MsgJoinAck (0x11)

```
[1B type][2B yourID][4B tick]
```

Сообщает клиенту его собственный `id` сущности и текущий тик.

### MsgSpawn (0x12)

```
[1B type][2B id][2B x][2B y]
```

Игрок `id` (пере)родился в точке (x, y) — координаты квантованы как в снапшоте.
Шлётся всем. Владельцу даёт сбросить предсказание на авторитетную точку спавна;
остальным — сразу поставить сущность, не дожидаясь снапшота.

### MsgDeath (0x13)

```
[1B type][2B victimID][2B killerID]
```

`victimID` убит `killerID`. Шлётся всем (kill feed). Мёртвый игрок исчезает из
снапшотов до респауна.

### MsgHit (0x14)

```
[1B type][2B attackerID][2B victimID][1B damage][1B victimHP]
```

`attackerID` попал по `victimID` на `damage` урона, HP цели стал `victimHP`.
Шлётся участникам (атакующему и жертве) для фидбэка.

Все три — reliable: в отличие от снапшотов, их нельзя дропать. Сессия, которая не
может их принять, помечается на отключение, а не теряет событие. Снаряды же
событий не порождают — они видны как сущности `KindProjectile` в снапшотах.

### MsgMatchState (0x15)

```
[1B type][1B phase][4B remaining][2B winner][1B flags][1B scoreCount]
scoreCount × [2B id][2B kills][2B deaths][1B team][2B hillScore][1B nameLen][name UTF-8, ≤ 16B]
```

Состояние матча (итерация 14, FFA deathmatch с таймером; командный режим — итер. 23;
King of the Hill — итер. 29). `phase`: `0` — идёт бой, `1` — антракт. `remaining` — тиков
до смены фазы (клиент отсчитывает таймер локально между обновлениями). `flags` — битовое
поле: бит `0` (`matchFlagTeamMode`) — командный режим, бит `1` (`matchFlagHillMode`) —
King of the Hill. `winner` в антракте валиден (иначе `0`): в FFA — id игрока-победителя,
в командном режиме — **id команды-победителя** (`0`/`1`); получатель различает по флагам.
`scoreCount` строк табло, отсортированы по убыванию первичного счёта (в hillMode — `hillScore`,
иначе `kills`), при равенстве — по возрастанию `id`; `team` — команда игрока (`0`/`1`,
всегда `0` в FFA); `hillScore` — очки контроля холма (`0` вне hillMode).

Reliable и **событийный**, не поллинг: комната шлёт его лишь когда табло реально
изменилось — смена фазы, чья-то смерть, вход/выход игрока, а также новичку сразу
при входе. В тишине провод молчит. Игровое ядро в бэкенд не течёт: сообщение
собирается в комнате из `World.MatchState()` (снимок состояния, вне `Checksum`).

**Командный режим (итер. 23).** Включается на сервере (`ARENA_TEAM_MODE`), фиксируется
при создании мира (`SetTeamMode` до первого join). Две команды, баланс при входе (в
меньшую), дружественный огонь выключен (снаряд проходит сквозь союзника). Команда игрока
(`Player.team`) и снаряда — состояние симуляции, **входит в `Checksum`**; сам флаг
`teamMode` — фиксированный параметр мира (как `tickRate`), в `Checksum` не входит, но
пишется в **лог реплея v2**, чтобы реплей реконструировал дружественный огонь верно.
Команда едет на клиент только этим сообщением (в снапшот/дельту не добавлена — горячий
путь не тронут); клиент строит карту `id→team` из табло и красит по ней сущности,
миникарту и табло.

**King of the Hill (итер. 29).** Включается на сервере (`ARENA_HILL_MODE`), фиксируется
при создании мира (`SetHillMode` до первого join). В центре арены — круглый холм; пока его
контролирует ровно одна сторона (в командном режиме — команда, иначе — отдельный игрок),
её игроки в зоне копят `HillScore`; при оспаривании (в зоне две и более сторон) очки не
растут. `HillScore` — состояние симуляции, **входит в `Checksum`**; сам флаг `hillMode` —
фиксированный параметр мира (как `teamMode`), в `Checksum` не входит, но пишется в **лог
реплея v4**. Геометрия холма (центр/радиус) статична, зеркалится клиентом (`SIM.Hill*`) —
координаты в проводе не едут. В hillMode табло сортируется и победитель считается по
`hillScore` (в проводе — то же поле в каждой строке), а не по фрагам; клиент рисует зону,
подсвечивая контролёра локально по игрокам внутри.

### MsgPickupState (0x16)

```
[1B type][1B count]
count × [1B spot][1B kind]
```

Состояние пикапов (итерация 19). Список **сейчас активных** точек: `spot` — индекс
фиксированной точки появления (клиент зеркалит их координаты в `PICKUP_SPOTS`, как
`WALLS`), `kind` — тип (`1` аптечка, `2` ускорение стрельбы, `3` веер). Это **полное**
состояние, не дельта: точка, которой нет в списке, считается пустой. Пикапы намеренно
не едут в снапшоте (иначе раздули бы дельту и пер-тик счётчики сущностей) — координаты
статичны и зеркалятся, а динамику (кто занят и чем) несёт это сообщение.

Reliable и **событийный**, как `MsgMatchState`: комната шлёт его при изменении (спавн
или подбор пикапа) и новичку при входе. Само состояние пикапов — часть симуляции и
входит в `Checksum` (спавн детерминирован `w.rng`, подбор — по позициям), но провод
(`MsgPickupState`) — лишь его проекция и в `Checksum` не входит.

### MsgKillstreak (0x17)

```
[1B type][2B id][2B streak]
```

Игрок `id` достиг вехи серии убийств длиной `streak` (итерация 20). Reliable, всем —
для объявления/фида и щит-визуала. Эмитится сервером на каждой `killstreakStep`-й фраге
без смертей. Сами серия (`Player.streak`) и окно неуязвимости (`Player.invulnUntil`) —
часть симуляции и входят в `Checksum`; это сообщение — лишь уведомление о вехе.

Окно неуязвимости (spawn protection) на проводе **отдельного сообщения не имеет**:
клиент рисует щит-кольцо от события `MsgSpawn` (респаун) и `MsgKillstreak` (веха) на
зеркалимую длительность — чисто косметика, сервер авторитетен (неуязвимость проверяется
в `findHit`, снимается выстрелом в `tryFire`).

### MsgWeaponState (0x18)

```
[1B type][1B count] count × [2B id][1B weapon]
```

Текущее оружие каждого игрока (итерация 26): `weapon` — тип (1 пистолет / 2 дробовик /
3 снайперка / 4 ракета). Полный набор (не дельта), reliable, всем — событийно при смене
оружия/входе (как `MsgPickupState`). Клиент строит карту id→оружие: HUD своего оружия и
подпись над бойцами. Выбранное оружие (`Player.weapon`) — часть симуляции и входит в
`Checksum`; это сообщение — лишь его проекция на клиент. Оружие в снапшоте не едет —
горячий путь снапшота/дельты не тронут. Само переключение приходит от клиента в старших
битах `buttons` (см. MsgInput выше), а не отдельным сообщением.

## Константы (единый источник — `protocol` + `game`)

| Константа       | Значение | Смысл                                  |
|-----------------|---------:|----------------------------------------|
| `MapSize`       |     4096 | сторона карты в юнитах                  |
| `CoordScale`    |       16 | шаг квантования координат (1/16 юнита)  |
| `MaxNameLen`    |       16 | максимум длины имени, байт             |
| `MaxEntities`   |      255 | максимум сущностей в снапшоте           |

> ⚠️ **Синхронизация с клиентом.** Клиент (`web/game.js`) зеркалит формат, игровые
> константы (скорость, радиус), общий шаг движения `Step` и шаг предсказания
> `PREDICT.dt = 1/InputRate`. При изменении протокола или движения правьте обе
> стороны в одном коммите, иначе рассинхрон проявится как «дрейф» предсказания, а
> не как ошибка компиляции.

## Golden- и fuzz-файлы

- `internal/protocol/testdata/*.golden` — эталонные байтовые дампы. Обновляются
  осознанно: `go test ./internal/protocol -update`, затем ревью диффа.
- Корпус фаззера (`testdata/fuzz/`) в git не коммитится (см. `.gitignore`);
  сид-корпус задан прямо в `FuzzDecode`.
