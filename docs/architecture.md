# Архитектура

Документ описывает устройство сервера на текущей итерации и модель
конкурентности, на которой держится весь проект. Обновляется по мере итераций.

## Слои и зависимости

```
                 ┌────────────────────────────────────────────┐
   браузер  ───► │ cmd/server (HTTP/WS gateway, конфиг, pprof) │
   (web/)  WS    └───────────────┬────────────────────────────┘
                                 │  transport.Conn
                     ┌───────────▼───────────┐
                     │        hub            │  менеджер комнат
                     └───────────┬───────────┘
                                 │  *game.Room
                     ┌───────────▼───────────┐
                     │        game           │  симуляция (без сети!)
                     │  room · world · step  │
                     │  clock · session      │
                     └───────────┬───────────┘
                                 │  protocol.* (типы + кодек)
                     ┌───────────▼───────────┐
                     │      protocol         │  данные, без игры и без сети
                     └───────────────────────┘
```

Жёсткие правила границ (проверяются глазами и `go vet`, позже линтером):

- **`protocol`** не импортирует ничего игрового и ничего сетевого. Его можно
  фаззить и бенчмаркать изолированно.
- **`game`** не знает про WebSocket — только `transport.Conn`. Симуляция
  запускается в тестах вообще без сети (`transport.Pipe`, `ManualClock`).
- **`transport`** прячет конкретный стек за интерфейсом `Conn`, чтобы позже
  добавить WebRTC DataChannel, не трогая игру.
- **`game`** не импортирует бэкенд (`store`/`account`/`api`/`persist`): результаты
  матчей уезжают в `persist` через канал `Config.PersistSink` (тип события — в `game`),
  стрелка зависимости только `persist → game`.
- **`botfill`** (итерация 17) — наполнитель комнат ИИ-ботами — тоже потребитель шва
  рядом с `hub`, а не часть симуляции: `game` его не импортирует (стрелка
  `botfill → game/bot/transport`). Боты — обычные клиенты через `transport.Pipe` +
  `room.Join`; наполнитель мир не трогает (только `Players()`/`Join`/`State` и закрытие
  `Conn`).

## Модель конкурентности

Центральный инвариант: **одна комната = одна горутина**. Игровое состояние
(`World`) не защищается мьютексами, потому что его трогает ровно один код —
game loop комнаты. Всё внешнее заходит в комнату через каналы.

```
                       ┌──────────────── Room.Run (1 горутина) ───────────────┐
   readPump ──input──► │                                                      │
   (на сессию)         │   inbox (chan event) ──► drainInbox ──► World.Step   │
   Join/Leave/State ──►│                                    └──► broadcast ───┼─► out (на сессию)
                       │                                    └──► dropLaggards │
                       └──────────────────────────────────────────────────────┘
                                                                   │
   writePump (на сессию) ◄──────────────────── out (chan []byte) ──┘
```

- **inbox** — единственный вход в комнату. Джойны, покидания, вводы и запросы
  состояния — всё это события `event`, обрабатываемые между тиками. `Input` —
  негарантированное событие: если inbox переполнен, ввод дропается (через ~16 мс
  придёт следующий), лишь бы не блокировать readPump.
- **out** — исходящая очередь сессии. Писать в неё и **закрывать** её имеет право
  только комнатная горутина (правило «закрывает только отправитель»). Очередь
  маленькая: устаревший снапшот бесполезен. При переполнении дропается самый
  старый снапшот; систематическое отставание → дисконнект. Game loop никогда не
  ждёт медленного клиента.

### Владение горутинами

Каждая горутина имеет владельца и явный путь завершения:

| Горутина            | Кто запускает      | Как останавливается                         |
|---------------------|--------------------|---------------------------------------------|
| `Room.Run`          | `hub`              | отмена контекста → доигрывает тик → `Done()` |
| `Session.readPump`  | `Session.Run`      | ошибка чтения / отмена контекста            |
| `Session.writePump` | `Session.Run`      | комната закрывает `out`, или ошибка записи  |
| `Filler.Run` (цикл) | `main`             | отмена контекста                            |
| бот: сессия+Drain+Autopilot | `Filler` (`wg`) | отмена контекста / закрытие `Conn`; `Wait` дожидается |
| pprof/HTTP servers  | `main`             | `srv.Shutdown` при graceful shutdown        |

`Session.Run` связывает read- и write-pump: падение любого из направлений
отменяет общий контекст сессии и роняет второе — полусессия бесполезна.

### Наполнитель ботов (итерация 17)

`internal/botfill` держит в занятой комнате `ARENA_BOT_FILL` игроков: reconcile-цикл на
своей горутине сверяет население (`hub.Rooms()` + `room.Players()`) и подключает/снимает
ботов. Боты — обычные клиенты (`transport.Pipe` + `room.Join`, автопилот из `internal/bot`),
поэтому мир они не трогают. Два тонких инварианта конкурентности:

- **Надёжное снятие.** Снять бота = закрыть клиентский конец `Pipe`. Серверная сессия внутри
  `Run` постит `leave`, пока её контекст ещё жив (`cancel` — в defer сессии, ПОСЛЕ возврата
  `Run`), поэтому отмена не гонится с постингом `leave` и игрок удаляется надёжно.
- **Барьер против «фантомных людей».** Сессия постит `leave` до `close(done)`, но комната
  обработает его лишь на тике; если выбросить бота из учёта по `done` раньше — на тик он
  выглядел бы человеком, и наполнитель добавлял бы замену бесконечно. Поэтому, увидев `done`,
  наполнитель зовёт `room.State(ctx)` (точка синхронизации) перед чтением `Players()`:
  happens-before (`leave` в inbox до `close(done)`; `done` виден до `State`; inbox FIFO)
  гарантирует, что `leave` уже обработан. Люди = `Players() − наши живые боты`.

Порядок shutdown в `main`: отмена контекста → `srv.Shutdown` → `hub.Wait` → `<-fillerDone`
→ `filler.Wait` → закрытие канала персиста. Комната при shutdown НЕ ждёт горутины сессий (их
владелец — наполнитель/шлюз), поэтому `hub.Wait` и `filler.Wait` не зависят циклически; боты —
гости (`AccountID 0`), персист не шлют.

## Жизненный цикл соединения

1. Браузер открывает WS на `/ws`. `transport.Upgrade` даёт `Conn`.
2. Gateway читает первый кадр — это должен быть `Join` (в пределах `JoinTimeout`).
3. `hub.Assign` выдаёт комнату с местом (или создаёт новую).
4. `room.Join` (через inbox) добавляет игрока в мир, создаёт `Session`, ставит в
   очередь `JoinAck` и возвращает сессию.
5. `Session.Run` крутит pumps до дисконнекта или shutdown.

## Graceful shutdown

SIGINT/SIGTERM отменяет базовый контекст в `main`. Дальше по цепочке:
HTTP-сервер перестаёт принимать соединения → комнаты доигрывают текущий тик и
закрывают сессии (закрывая `out`, что завершает writePump) → `hub.Wait`
дожидается остановки всех комнат. Тик никогда не прерывается на полпути —
мир не остаётся в полупросчитанном состоянии.

## Детерминизм

Симуляция обязана быть детерминированной — это фундамент реплеев и клиентского
предсказания. Поэтому внутри `game`:

- обход игроков — только по отсортированному срезу `order`, не по map;
- случайность — только через `World.rng` (seeded PCG), не через глобальный `rand`;
- время — только через `Clock`, не через `time.Now()` напрямую в логике.

Тест `TestWorldDeterminism` гоняет два мира с одним seed и одной лентой вводов и
сверяет `World.Checksum()` побайтово. Подробнее — в [testing.md](testing.md).

## Частота снапшотов (итерация 2)

Тикрейт 30 Гц, но снапшоты уходят на 20 Гц — реже, чем считается мир. 20 не
делит 30 нацело, поэтому используется делитель частоты по Брезенхэму
(`rateDivider`): накопитель растёт на `SnapshotRate` каждый тик и, перевалив за
`TickRate`, выпускает снапшот и вычитает `TickRate`. Это даёт ровно 2 снапшота на
3 тика, равномерно. Разрыв между сервером и клиентом скрывает клиентская
интерполяция: клиент буферизует снапшоты и рендерит мир на 100 мс в прошлом,
интерполируя позиции между двумя соседними снапшотами на серверной шкале времени.

## Lag compensation (итерация 5)

Клиент из-за интерполяции (рендер на 100 мс в прошлом) и RTT видит цели в прошлом.
Чтобы попадания считались по тому, что игрок реально видел, сервер перематывает
цели во времени. Каждый игрок держит кольцо `posHist` — позиции за последние
`historyLen` тиков, записываемые каждый тик под меткой `Snapshot.tick`. В каждом
вводе клиент шлёт `ViewTick` — серверный тик, к которому он интерполировал. При
выстреле сервер фиксирует на снаряде постоянный сдвиг `rewind = clamp(now −
ViewTick, 0, maxRewindTicks)` и на каждом тике полёта проверяет попадание против
позиции цели из истории на `rewind` тиков назад — снаряд и «отмотанная» цель идут
в локстепе, воспроизводя ровно то, что видел стрелок. Кламп окна — анти-чит:
отмотать цель произвольно далеко нельзя. Кольцо истории и `rewind` входят в
`Checksum` — это будущее состояние, от которого зависит следующий hit-тест.

## Interest management (итерация 6)

Полный бродкаст шлёт каждому клиенту весь мир — трафик растёт линейно с числом
игроков в комнате. Interest management (area of interest, AOI) это разрывает:
клиент получает только сущности в своей окрестности, поэтому платит за то, что
видит, а не за всю комнату.

Механика. После `Step` комната раскладывает сущности снапшота по равномерной
пространственной сетке (`aoiGrid`, клетка 256 юнитов, 16×16 клеток на карту
4096²). Для каждого зрителя она запрашивает клетки, пересекающие коробку
`±AOIRadius` вокруг его игрока (широкая фаза), уточняет попадание точным фильтром
коробки и кодирует получившееся подмножество. Мёртвый зритель центрируется на
точке смерти (death-cam до респауна); себя игрок видит всегда — он в центре.
`AOIRadius == 0` (по умолчанию для `Config`) выключает AOI и возвращает полный
бродкаст — на этом режиме держатся тесты итераций 1–5; боевой сервер включает AOI
через `ARENA_AOI_RADIUS` (по умолчанию 640).

Границы. AOI — **networking, а не симуляция**: сетка и подмножества строятся из
уже просчитанных позиций, читаются только на пути рассылки и ни во что во `World`
не пишут. Поэтому сетка **не входит в `Checksum`** (это производный индекс уже
хешируемых позиций) и на реплеи/детерминизм не влияет. Клиенту правки не нужны:
его интерполяция уже терпима к появлению/исчезновению сущностей из набора —
сущность, вышедшая из вида, для клиента неотличима от ушедшей из игры. Порядок
подмножества стабилизирован (игроки раньше снарядов, внутри — по возрастанию id):
это держит кодирование детерминированным и готовит согласованные базы для
дельт (итерация 6B). Сетка и её буферы принадлежат горутине цикла — как и `World`,
без синхронизации.

## Дельта-кодирование снапшотов (итерация 6B)

Interest management срезал число сущностей на клиента; дельты срезают байты на
сущность. Каждый снапшот уходит либо полным, либо дельтой против недавнего
снапшота, который клиент подтвердил.

Механика (модель Quake3/Source). Клиент шлёт в каждом `Input` метку последнего
реконструированного снапшота (`AckTick`). Сервер держит на каждую сессию кольцо
последних отправленных ей наборов сущностей. Кодируя очередной снапшот, он берёт
подтверждённую базу из кольца и шлёт только то, что изменилось на проводе
(`EntityFieldMask` сравнивает квантованные поля, поэтому субквантовое дрожание не
идёт в дельту) плюс список ушедших id. Если база выпала из кольца (клиент сильно
отстал/большой RTT) или дельта не короче полного — шлётся полный снапшот. Разница
считается слиянием двух указателей по общему порядку `entityKey` (игроки раньше
снарядов, внутри по id) — без аллокаций и без map.

Реконструкция — на получателе: поверх копии базы применяется remove, затем
changed. Три стороны делают это одинаково: сервер (`sendSnapshot`), браузерный
клиент (`web/game.js`, `applyDelta`) и headless-бот (`internal/bot`,
`reconstructor`) — на этом же пути бот подтверждает тики, поэтому e2e и нагрузка
гоняют дельту по-настоящему. Инвариант корректности: клиент подтверждает только
тик, который держит у себя, поэтому база дельты у него всегда есть; если сервер
эту базу уже вытеснил — он шлёт полный.

Границы те же, что у AOI: это **networking**. Пер-сессионное состояние (ackTick,
кольцо баз) принадлежит горутине комнаты, в `World.Checksum` не входит и на
детерминизм/реплеи не влияет. Клиентская реконструкция байт-точна (хранит
деквантованные значения и переигрывает их), поэтому база сервера и набор клиента
совпадают на проводе тик-в-тик.

## Нагрузка и пул буферов (итерация 6C)

`cmd/loadtest` поднимает одну комнату на N ботов in-process (через `transport.Pipe`)
и меряет tick p50/p99/max, сущности в снапшоте и трафик на клиента. Pipe, а не сеть:
tick p99 — работа горутины комнаты, сокет в неё не входит, поэтому Pipe даёт ту же
тик-стоимость без сетевого джиттера, воспроизводимо. На 200 ботах в одной комнате
tick p99 ≈ 2.5 мс (цель < 15 мс), сущностей в снапшоте ~27 из 200 (AOI), трафик
~7 КБ/с против ~48 КБ/с полного бродкаста — числа в [BENCHMARKS.md](../BENCHMARKS.md).

Пул буферов снапшотов (`Room.snapPool`, `sync.Pool` по `*[]byte`) снимает аллокацию
буфера на каждый снапшот на клиента: комната берёт буфер в `sendSnapshot`, write
pump сессии возвращает его после записи (транспорт данные копирует, поэтому
переиспользование безопасно), выброшенные из очереди — тоже. Владение чёткое: буфер
в любой момент держит ровно один — либо пул, либо его текущий обладатель.

## Реплеи (итерация 7)

Детерминизм — фундамент, и итерация 7 делает его инструментом. Мир пишет лог: `seed`
и все **принятые** события (join/leave/input) со **штампом тика** (`replay.go`).
Штамп обязателен: `World.Step` осушает вводы пачками, поэтому реплей подаёт те же
события в те же тики перед тем же `Step`. `game.Replay(log)` реконструирует мир (тот
же `NewWorld` + те же мутации) и возвращает `Checksum`; `cmd/replay [-verify]`
проигрывает лог headless и сверяет хэш — пойманный desync становится регрессией.

Запись живёт во `World` (хуки в `AddPlayer`/`RemovePlayer`/`EnqueueInput`), поэтому
любой мир — из комнаты или из теста — пишется одинаково, а реплей (голый `World`)
симметричен. Опт-ин: без `Config.RecordReplay`/`EnableReplayRecording` это только
nil-проверка, горячий путь не растёт. Пишутся лишь принятые вводы: дропнутый дедупом
повтор `lastQueuedSeq` не меняет. В итерации 7 закрыто слепое пятно `Checksum`:
`lastQueuedSeq`/`hasQueued` — тоже будущее состояние (гейт приёма вводов) — теперь
входят в хэш, и реплей воспроизводит их точно.

Формат лога версионируется: v2 (итер. 23) добавил в заголовок `teamMode`, v3 (итер. 29) —
байт `Actions` в input-событии (рывок `ActDash` из итер. 27 влияет на движение и входит в
`Checksum`, поэтому обязан ехать в логе; до v3 реплей с рывками рассинхронивался). Всё,
что влияет на симуляцию, но не выводится из вводов, обязано попасть в лог — иначе реплей
разойдётся; декодер принимает и старые версии.

## Препятствия/стены (итерация 10)

Арена получила статичные препятствия — выровненные по осям коробки (AABB) с
фиксированной раскладкой (`walls.go`, `var walls`). Игрок сталкивается со стеной
как круг, снаряд — как отрезок.

Коллизия игрока живёт в общем шаге `Step`: после клэмпа к границам карты
`resolveWalls` выталкивает круг радиуса `PlayerRadius` из каждой стены — проекция на
ближайшую точку коробки и сдвиг по нормали, а вырожденный случай «центр внутри»
(туннелирование) выходит через ближайшую грань. Раз это внутри `Step`, клиент
повторяет коллизию тем же кодом при предсказании (`web/game.js`, `resolveWalls` в
`stepMove`) — иначе своя позиция задрейфила бы. Проход один за шаг: за тик игрок
сдвигается на единицы юнитов (стены толще шага), остаток исправит следующий тик.

Коллизия снаряда — в `stepProjectiles`: `segmentWallHit` (метод слэбов, отрезок vs
расширенный на радиус снаряда AABB) находит ближайшую задетую стену; снаряд гибнет,
а сегмент проверки попадания подрезается до точки входа — цель перед стеной урон
получает, за стеной нет.

Спавн избегает стен: `spawnPoint` перебрасывает точку через `w.rng`, пока она не
выйдет из препятствий (детерминированно — реплей воспроизводит те же розыгрыши).

Границы. Стены статичны и одинаковы во всех мирах, поэтому в `Checksum` их нет: в
хэш уже входят исправленная коллизией позиция игрока (X/Y) и факт удаления снаряда
(`w.projectiles`) — само́ следствие. Новое наблюдаемое состояние коллизия не
добавляет, лишь меняет уже хешируемое. Раскладка `walls` зеркалится в `web/game.js`
(`WALLS`) — координаты **и порядок** обязаны совпадать (порядок влияет на разрешение
коллизий), по тем же правилам, что и формат протокола.

## Транспорт WebRTC DataChannel (итерация 11)

Игровой код всегда видел только `transport.Conn` — под это транспортная абстракция и
строилась. Итерация 11 добавляет вторую реализацию `Conn` поверх WebRTC DataChannel
(pion на сервере, `RTCPeerConnection` в браузере) рядом с WebSocket; симуляция, кодек
и сессии не тронуты. Транспорт выбирается явно (`web/game.js` `?transport=webrtc`),
фолбэка нет: `/ws` остаётся дефолтом и путём ботов/e2e.

Границы. Весь pion живёт в `internal/transport` (`webrtc.go`) и наружу не протекает.
`AcceptWebRTC` (сервер-answerer) и `DialWebRTC` (клиент-offerer) принимают уже
установленный сигналинг-`Conn` и возвращают игровой `Conn` — тот же `rtcConn`.
`cmd/server` про pion не знает: `/rtc` апгрейдит сигналинг-WS и передаёт его в
`AcceptWebRTC`, а дальше — общий `gateway.serve`, тот же, что у WebSocket.

Сигналинг. Три JSON-сообщения по WS: сервер шлёт `config` (ICE-серверы из
`ARENA_STUN`), клиент — `offer`, сервер — `answer`. JSON здесь допустим — сигналинг
не горячий путь (в отличие от игрового кодека). ICE — **non-trickle**: обе стороны
собирают всех кандидатов до отправки SDP (`GatheringCompletePromise`), поэтому
отдельных candidate-сообщений и фоновой горутины сигналинга нет; на localhost/LAN
хватает host-кандидатов, `ARENA_STUN` добавляет STUN/TURN для NAT. Сигналинг-WS живёт
только на рукопожатие и закрывается до старта игры.

DataChannel "game" создаётся ordered+reliable (дефолт pion) — семантически как
WebSocket, поэтому reliable-события (Hit/Death/Spawn) и дельты с ack работают без
изменений. Конкурентность `rtcConn`: входящие сообщения приходят колбэком `OnMessage`
с горутины pion в буферизованный канал `recv` (переполнение тормозит колбэк —
backpressure, а не потеря reliable-кадра); `Read` селектит `recv`/`done`/`ctx`.
Собственных горутин `rtcConn` не заводит — pion-горутины принадлежат
`PeerConnection`, а путь их завершения — `pc.Close()` в идемпотентном `shutdown()`
(сначала `close(done)` — будит колбэк и `Read`, потом `pc.Close()`). Клиент зеркалит
это в `web/game.js` (`connectWebRTC`, DataChannel `binaryType='arraybuffer'`).

## WebRTC до продакшена: TURN + unreliable снапшоты (итерация 12)

Итерация 11 дала один reliable-канал (семантика WS). Итерация 12 доводит WebRTC до
боевого уровня двумя независимыми улучшениями; провод (`internal/protocol`) не тронут.

**Два DataChannel по ценности сообщений.** У сообщений она разная, поэтому и каналов
теперь два:

- **"game"** — ordered+reliable (дефолт SCTP): JoinAck, Spawn/Death/Hit, вводы. Терять
  нельзя — семантика WebSocket.
- **"state"** — unordered+unreliable (`MaxRetransmits=0`): снапшоты. Устаревший снапшот
  бесполезен, ретрансмитить его незачем; а на надёжном канале потерянный пакет держал
  бы **head-of-line blocking** — все следующие снапшоты ждали бы его повтора. Отдельный
  unreliable-канал убирает и это, и блокировку reliable-событий за снапшотами.

Оба канала создаёт offerer (клиент/`DialWebRTC`), answerer (сервер/`AcceptWebRTC`)
принимает их через `OnDataChannel` и роутит по метке (`bindChannel`). Направление
данных: "game" двунаправлен, "state" — только сервер→клиент. Reliable-путь наружу —
`Conn.Write`, unreliable — новый **опциональный** интерфейс `transport.UnreliableWriter`
(`WriteUnreliable`). Снапшоты на него роутит `Session`: решение принимается один раз в
`newSession` (type-assert на `UnreliableWriter`); транспорт без best-effort режима
(WebSocket, `Pipe`) интерфейс не реализует — снапшоты идут обычным `Write`, поведение
ровно прежнее, без регресса. Так разделение надёжности выражено на границе транспорта,
а не протечкой кодов сообщений в транспорт.

Устойчивость клиента к дропам/reorder уже была заложена дельта-механизмом: клиент
подтверждает (`ackTick`) только реконструированный тик, сервер держит кольцо баз и при
выпавшей базе шлёт полный снапшот; `pushSnapshot` игнорирует переупорядоченные тики.
Добавлена лишь защита `ackTick` от отката на устаревшем снапшоте (`lastSnapTick`).

Конкурентность `rtcConn` (двухканальный). Поля `dcReliable`/`dcUnreliable` ставятся в
`bindChannel` под `mu` (это транспортное plumbing, не состояние симуляции); `opened`
закрывается, когда открыты **оба** канала (`onChannelOpen`, тот из колбэков, что
последним увидел оба открытыми) — чтобы первый же `WriteUnreliable` не ушёл в ещё не
открытый канал. После `awaitOpen` поля неизменны, и `Write`/`WriteUnreliable` читают их
без `mu` (happens-before через `close(opened)`). Оба канала кладут в один `recv` —
читатель различает сообщения по типу, не по каналу. Своих горутин по-прежнему нет.

**TURN для обхода NAT.** `ICEServer` теперь несёт `Username`/`Credential` — TURN нужны
статические креды. Env: `ARENA_STUN` (STUN URL), `ARENA_TURN` + `ARENA_TURN_USER`/
`ARENA_TURN_PASS` (TURN URL и креды). `ARENA_FORCE_RELAY` включает
`ICETransportPolicy=relay` — соединение **только** через TURN (host/srflx-кандидаты
отброшены): для жёстких сетей/симметричного NAT и приватности (реальный IP пира не
светится). ICE-серверы и relay-политику задаёт сервер и передаёт клиенту в `config`-
сигналинге (обе стороны собирают согласованных кандидатов). Покрытие: `TestWebRTCTURNRelay`
поднимает in-process TURN-сервер (`pion/turn`) и гоняет DataChannel relay-only —
доказывает, что TURN-путь работает от конфига до открытого канала.

## Бэкенд: аккаунты, статистика, история (итерация 13)

Персистентный бэкенд, **архитектурно отделённый** от игрового ядра — модульный монолит
с жёсткими границами, чтобы части можно было разнести позже. `internal/game` бэкенд
**не импортирует**: результаты матчей едут через отдельный persister (итерация 14B, ниже),
а не из горутины комнаты, которая не должна блокироваться на БД.

- `internal/store` — интерфейс `Store` (аккаунты, статистика, матчи) и одна SQL-
  реализация, параметризованная диалектом: **SQLite** (dev/CI, pure-Go, без внешней
  СУБД) и **PostgreSQL** (prod). Отличий диалектов всего два — стиль плейсхолдеров
  (`?` / `$N`) и возврат id (`LastInsertId` / `RETURNING`); остальной SQL общий.
  Миграции встроены (`embed.FS`) и применяются на старте с версионированием
  (`schema_migrations`). Таймстемпы — unix-millis, булевы — `INTEGER 0/1`: единый
  маппинг, независимый от драйвера. `store` не знает про игру и сеть.
- `internal/account` — идентичность: гость + аккаунты. Пароли — argon2id (PHC-строка).
  **Токены (итерация 36):** короткий **access** — самодостаточный подписанный токен
  (`base64url(json).base64url(hmac_sha256)`), проверяемый без обращения к БД (им
  авторизуются и API, и game-join); долгий **refresh** — непрозрачная случайная строка,
  живущая в `store` (хранится только её SHA-256), с **ротацией**: каждый `Refresh`
  отзывает предъявленный токен и выдаёт новый в том же `family_id`. Повторное предъявление
  уже отозванного токена трактуется как кража — гасится всё семейство (`RevokeRefreshFamily`);
  `Logout` отзывает семейство явно. Отзыв старого при ротации атомарен (транзакция,
  `UPDATE … WHERE revoked_at = 0`; 0 затронутых строк → `ErrTokenRevoked`), просроченные
  токены аккаунта чистятся там же (таблица ограничена сроком жизни). Гость эфемерен: имя
  живёт в access-токене, строки в БД нет (`AccountID == 0`), refresh не выдаётся.
  **Email + сброс пароля (итерация 37):** аккаунт может нести опциональный email
  (уникальный частичным индексом) и флаг верификации; одноразовые токены верификации/
  сброса живут в `account_tokens` (снова только SHA-256, `kind` различает назначение,
  `used_at` даёт одноразовость через `ConsumeAccountToken` — атомарная пометка под
  гонкой). `RequestPasswordReset` не раскрывает существование аккаунта (всегда без
  ошибки), `ResetPassword` меняет пароль и отзывает ВСЕ refresh-токены аккаунта
  (`RevokeAllRefreshTokens` — разлогин везде). Доставка писем — за интерфейсом `Mailer`
  (`WithMailer`); без SMTP по умолчанию `LogMailer` печатает токен в лог (только dev).
  **Роли, баны, репорты (итерация 39):** роль аккаунта (`user`<`moderator`<`admin`, ранг
  в `roles.go`), баны (`bans`: история; активный — `lifted_at=0` и не истёк — считает
  `ActiveBan`) и репорты (`reports`). `IsBanned` — тонкая обёртка над `ActiveBan` для
  шлюза и `/api/me`. Знает только `store` и криптографию.
- `internal/api` — REST на чистом `net/http` (роутинг метод+паттерны Go 1.22), JSON.
  Авторизация — `Authorization: Bearer <access>` → `account.Verify`. `POST /api/refresh`
  меняет refresh на новую пару, `POST /api/logout` отзывает семейство (204); `verify-email`/
  `request-password-reset`/`reset-password` — верификация email и сброс пароля (итер. 37).
  **Модерация (итер. 39):** `report` (любой залогиненный), `mod/ban`/`mod/unban`/`mod/reports`
  (moderator+), `mod/role` (admin) — под `requireRole`, который тянет АКТУАЛЬНУЮ роль из БД
  (не из токена — роль могла смениться); бан отзывает все сессии, `/api/me` несёт роль и
  статус бана. `mod/anticheat` (moderator+, итер. 40) — топ по накопленным античит-событиям. Домены ошибок мапятся в HTTP-коды (validation→400, taken→409, credentials/
  token→401, forbidden→403, not-found→404). Token-минтящие/письмо-рассылающие POST'ы (`register`/`login`/`guest`/
  `refresh`/`verify-email`/`request-password-reset`/`reset-password`) прикрыты пер-IP токен-бакетом
  (`ratelimit.go`, итерация 21): ёмкость `Burst`, дозаправка `Burst/Window`, исчерпал —
  `429`+`Retry-After`. Сам токен-бакет живёт в общем `internal/ratelimit` (итер. 33; тот же
  примитив у шлюза игрового входа), здесь — тонкий HTTP-адаптер. Всё под мьютексом, фоновых
  горутин нет — простаивающие бакеты подчищаются ленивым свипом на запросе, часы инъектируемы
  для тестов. Env `ARENA_AUTH_RATE_*`.
- `internal/persist` (итерация 14B) — шов игра → БД. Комната шлёт game-определённые
  события (`PersistMsg`: смерть / итог матча / **античит-событие**, итер. 40) в
  `Config.PersistSink chan<- PersistMsg` **неблокирующе** (`select`/`default`:
  переполнение роняет статистику, тик не стоит на I/O). Persister читает канал в СВОЕЙ
  горутине и переводит события в вызовы `Store`: kills/deaths копятся вживую по смертям
  (переживает дисконнект), games/wins + история — на итог матча (`RecordMatch` не
  задваивает kills/deaths). **Античит (итер. 40):** `tryFire` привязывает клампнутое
  событие к `AccountID` игрока в транзиентный `acEvents` (вне Checksum/реплея, как
  счётчики `ac` итер. 25); комната шлёт их persister'у, тот копит в `anticheat_stats` и
  при пороге (`Config.AntiCheatBanThreshold`, по умолчанию 0 — выкл) автобанит с отзывом
  сессий. Импортирует `game`+`store`; `game` его НЕ импортирует (стрелка только
  persist→game). Гости (`AccountID 0`) в БД не пишутся.
- `cmd/server` — открывает `Store` (env `ARENA_DB_DRIVER`/`ARENA_DB_DSN`), поднимает
  `account.Service` (`ARENA_AUTH_SECRET`, пусто — эфемерный секрет с предупреждением),
  запускает persister и монтирует `/api/` рядом с `/ws`,`/rtc`. Джойн несёт токен: шлюз
  `resolveIdentity` проверяет его (`account.Verify`) и привязывает сессию к аккаунту (имя
  берётся из токена — анти-имперсонация), иначе гость. **Бан (итер. 39):** сразу после
  `resolveIdentity` шлюз зовёт `accounts.IsBanned` и закрывает соединение забаненному ДО
  входа в комнату (игровое ядро про баны не знает); при ошибке БД — fail-open (пускаем,
  логируем). При старте `ARENA_ADMIN_USERNAME` повышает аккаунт до admin (бутстрап). Тот
  же процесс, общий `Store`. **Рейт-лимит входа (итер. 33):** `/ws` и `/rtc` обёрнуты
  `joinGate` — пер-IP кап живых соединений (`ratelimit.ConnLimiter`, слот занят на время
  сессии: обработчик блокируется весь её срок) и токен-бакет скорости новых
  (`ratelimit.Limiter`), общие на оба транспорта; исчерпал — `429` до апгрейда, метрика
  `arena_join_rejected_total{reason}`. Env `ARENA_JOIN_*`.
- `internal/ratelimit` (итер. 33) — чистый примитив контроля доступа по ключу (без
  HTTP/игры/сети): токен-бакет скорости (`Limiter`) и кап конкурентных занятостей
  (`ConnLimiter`), плюс `ClientKey` (ключ из адреса пира / доверенного заголовка).
  Общий для auth-лимита (`internal/api`, итер. 21) и шлюза игрового входа (`cmd/server`).
  Конкурентно-безопасен под мьютексом, без фоновых горутин (карты чистятся лениво).

Конкурентность: `store` конкурентно-безопасен (`database/sql`; у SQLite один коннект —
`:memory:` у каждого соединения свой, а редкую запись сериализуем). Persister — одна
горутина, владелец `cmd/server`; её вход-канал закрывается при shutdown ПОСЛЕ `h.Wait()`
(все комнаты-отправители остановлены → закрывать безопасно), затем слив с таймаутом grace.
Новых игровых горутин/каналов бэкенд не вводит, модель «одна комната = одна горутина» не
тронута: `PersistSink` — единственный канал наружу, отправка из горутины цикла неблокирующая.

## Жизненный цикл матча (итерация 14)

FFA-deathmatch с таймером: раунд на время, счёт, победитель, антракт и авторестарт —
всё в симуляции, детерминировано. У игрока `Kills`/`Deaths`, во `World` —
`matchPhase`/`matchAt`/`winner`. `stepMatch` в общем `Step` гонит переходы по `w.Tick`
(`matchActive` `matchDurationTicks`=5400 → `matchIntermission` `intermissionTicks`=300 →
новый матч). `endMatch` фиксирует победителя (`leader()` — обход `w.order`, tiebreak по
минимальному id); `startMatch` обнуляет счёт и респаунит через `w.rng`; фраги/смерти
считаются в `applyDamage`. Всё новое состояние (Kills/Deaths, phase/matchAt/winner) —
будущее, поэтому **в `Checksum`**; длительности — константы (не конфиг), реплей-безопасны.

Провод: reliable `MsgMatchState` (0x15) шлётся **событийно, не поллингом** — при смене
фазы / смерти / входе-выходе + новичку сразу; в тишине провод молчит. Комната своих
горутин не заводит, буферы табло — на горутине цикла. Персист-половина (games/wins +
история матчей) — в бэкенд-секции выше (persister, 14B).

## Пикапы: оружие и бонусы (итерация 19)

Бонусы на фиксированных точках арены: **аптечка** (мгновенный хил), **ускорение
стрельбы** и **веер** (временные буфы, чистятся при респауне). `pickups.go`: точки
`pickupSpots` (обход по индексу), `stepPickups` в `Step` (фаза 4, после респауна, до
`Tick++`) активирует созревшие точки (тип через `w.rng.IntN`, тайминг — по `w.Tick`) и
отдаёт активный пикап игроку с МЛАДШИМ id (обход `w.order`). Эффекты: аптечка —
`min(100, HP+heal)`; ускорение/веер — таймер-буфы `Player.rapidUntil`/`spreadUntil`,
которые читает `tryFire`; `respawn` их чистит. Всё новое сим-состояние (буфы +
`active/kind/readyAt` каждой точки) — **в `Checksum`**; `pickupsDirty` — networking-флаг,
в `Checksum` НЕ входит.

Провод: reliable `MsgPickupState` (0x16) — полный набор активных точек, событийно
(`broadcastPickups` при `PickupsDirty` + новичку). Пикапы в снапшоте НЕ едут (раздули бы
дельту): координаты точек статичны и зеркалятся клиентом (`PICKUP_SPOTS`, как `WALLS`),
динамику несёт это событийное сообщение. Клиент — чистый рендер, подбор авторитетен на
сервере (в предсказание не входит, дрейфа нет).

## Киллстрики и окно неуязвимости (итерация 20)

Две боевые механики, обе — детерминированная симуляция (в `Checksum`, без розыгрышей rng).
**Окно неуязвимости:** `Player.invulnUntil`; `respawn` ставит его на `spawnInvulnTicks`
(~2 c) — свежереспаунившийся неуязвим, `findHit` его пропускает (снаряд проходит насквозь,
урона/событий нет) — анти-спавн-килл. Щит спадает, как только игрок сам стреляет (`tryFire`
→ `invulnUntil = 0`). Только респаун (не первичный `AddPlayer`). **Киллстрики:**
`Player.streak` — серия убийств без смертей; растёт в `applyDamage` за фраг, обнуляется в
смерти и в `startMatch`. Каждые `killstreakStep`(3) фрага подряд — веха (`recordKill`):
хил до 100 + короткий щит + reliable `MsgKillstreak` (0x17) через event-пайплайн. Снапшот/
дельта не тронуты. Тест-эталон `findHitBruteforce` получил тот же invuln-скип для паритета
с `findHit`. Клиент: щит-кольцо + баннер серии — чистый рендер.

## Спектатор/наблюдатель (итерация 22)

Присоединение к комнате БЕЗ спавна. Ключевое: наблюдатель — чисто **сетевой** концепт на
уровне комнаты, в `World`/`Checksum`/симуляцию НЕ входит вовсе (детерминизм не тронут).
Провод: `Join.Spectator` — опциональный завершающий байт (обратная совместимость: старый
формат = обычный игрок); `MsgJoinAck` наблюдателю несёт `YourID == 0` — sentinel «своей
сущности нет» (`allocID` стартует с 1, 0 никогда не валиден). `Session.spectator` (readPump
НЕ форвардит его `MsgInput` — id наблюдателя не попадёт в `World.EnqueueInput`). Наблюдатели
живут в `Room.spectators` отдельно от `sessions` (ключ — room-local `nextSpecID`, в
пространство id сущностей не попадает), в `Players()` не видны. Им шлётся весь мир
(`broadcastSpectators`, всегда полный снапшот — ack не шлют) и reliable-события
(`reliableAll` обходит и sessions, и spectators). `removeSpectator` закрывает очереди как
`removeSession`, но `World` не трогает. Клиент — свободная камера на WASD.

## Командный режим (итерация 23)

Две команды, баланс при входе, дружественный огонь выключен, счёт/победитель по командам —
детерминированная симуляция (в `Checksum`, реплей-безопасна, без rng). `Player.team` (0/1)
ставится в `AddPlayer` детерминированным балансом `smallerTeam()` (обход `w.order`, в
меньшую команду) и дальше неизменна; `projectile.team` = команда стрелка. `findHit`
пропускает цель той же команды (`teamMode && tgt.team == pr.team`). `endMatch` в teamMode
кладёт в `w.winner` id ПОБЕДИВШЕЙ КОМАНДЫ (`winningTeam()` — больше суммарных фрагов,
tiebreak → 0), в FFA — id игрока (`leader()`); получатель различает по флагу. Новое
СОСТОЯНИЕ (`Player.team`, `projectile.team`) — **в `Checksum`**; сам флаг `teamMode` —
фиксированный параметр мира (как `tickRate`), в `Checksum` НЕ входит, но пишется в **лог
реплея v2** (`SetTeamMode` до первого join; декодер принимает и v1 FFA-логи).

Провод: `MsgMatchState` получил `[1B flags]` (бит0 = teamMode) после winner и `[1B team]` в
каждой строке табло. Снапшот/дельта не тронуты — команда едет только этим событийным
сообщением. `NewRoom` зовёт `world.SetTeamMode(true)` до первого join (happens-before старта
горутины цикла). Env `ARENA_TEAM_MODE`. Клиент зеркалит формат и раскрашивает по командам.

## Античит-метрики (итерация 25)

Наблюдаемость поверх УЖЕ существующего анти-чита (кламп окна перемотки `clampRewind`) —
сервер и без метрики авторитетно зажимает, счётчик лишь делает попытки видимыми оператору.
Метрика: Prometheus `arena_anticheat_events_total{kind}`, метки `rewind_stale` (`ViewTick`
дальше окна перемотки в прошлое — задержка/lag-switch) и `rewind_future` (`ViewTick` из
будущего — рассинхрон часов/подмена времени). Счётчики — транзиентное поле
`World.ac [antiCheatKindCount]uint64`: инкремент в `tryFire` перед `clampRewind` (по знаку/
величине `d = now − ViewTick`), на исход выстрела НЕ влияет. **В `Checksum` НЕ входят** и в
лог реплея не пишутся — реплей-безопасно. Слив — `DrainAntiCheat()`.

Шов: метка — строка в интерфейсе `game.Recorder.AntiCheat(kind string, n int)`, чтобы
`internal/metrics` не импортировал `game`. Enum `AntiCheatKind`+`String()` живёт в `game`,
комната переводит в метку. `reportAntiCheat()` сливает после каждого тика в `tick()` — всё
на горутине комнаты (мутация в `Step`, слив там же), новых горутин/каналов нет.

## Система оружия (итерация 26)

У игрока есть выбранное оружие, задающее картину выстрела: число дробин, разброс,
урон, кулдаун, скорость снаряда и (для ракеты) сплэш по площади. Четыре типа —
пистолет (базовый), дробовик (веер дробин), снайперка (одна быстрая пуля, большой
урон), ракета (детонация по площади). Всё детерминированная симуляция (в `Checksum`,
реплей-безопасно).

**Состояние.** `Player.weapon` — ВЫБРАННОЕ оружие (в `Checksum`: определяет будущий
выстрел; переживает респаун). `projectile.weapon` — оружие, которым СТРЕЛЯЛИ (снаряд
несёт его с собой — стрелок мог сменить оружие в полёте; урон/сплэш при попадании
берутся из спека этого оружия; тоже в `Checksum`). `weaponSpecs` — фиксированная
таблица характеристик; как `walls`/`pickupSpots` она одинакова во всех мирах, поэтому в
`Checksum` НЕ входит (в хэш идут её следствия — `vx/vy` снаряда, изменения HP).

**Переключение — через ввод, без нового формата провода.** Выбор оружия едет в
СТАРШИХ битах `Input.Buttons` (биты 5..7, `WeaponSelect`): 0 — «не менять», 1..4 —
выбрать. Формат ввода на проводе не меняется (по-прежнему один байт `Buttons`), движение
и огонь (биты 0..4) не затрагиваются. `Step` обрабатывает выбор ДО выстрела, поэтому
«сменил и выстрелил» одним фреймом стреляет уже новым оружием. Смена детерминирована
и реплей-безопасна (ввод пишется в лог реплея как обычно).

**Сплэш ракеты.** При контакте (игрок ИЛИ стена) ракета детонирует в точке удара:
`explode` наносит урон по площади с линейным спадом от `splashDamage` в эпицентре до 0
на границе `splashRadius`. Обход целей — по `w.order` (детерминированно), дистанция —
`math.Sqrt` (детерминирована в пределах арки, как `Cos/Sin` в `spawnProjectile`); цели
перематываются тем же `rewind`, что и прямое попадание (lag comp). Владельца сплэш не
задевает (нет самоурона), мёртвых/неуязвимых (итер. 20)/союзников (итер. 23) пропускает —
как прямое попадание.

**Провод (networking).** Текущее оружие каждого игрока едет отдельным reliable-
сообщением `MsgWeaponState` (0x18) — полный набор, событийно при смене/входе (как
`MsgPickupState`); снапшот/дельта и их пер-тик счётчики сущностей НЕ тронуты. Оружие в
снапшоте не едет. Клиент строит карту id→оружие (HUD своего оружия, подпись над
бойцами) и всегда шлёт текущий выбор в старших битах `Buttons`. Кодек zero-alloc,
bounds-checked; round-trip/fuzz/golden. Комната своих горутин не заводит — `weaponsDirty`
и буферы кодирования на горутине цикла.

**Взаимодействие с бафами (итер. 19).** Баф ускорения режет кулдаун любого оружия
(÷3, не меньше 1); баф веера превращает ОДНОдробинное оружие в `spreadCount`-веер (у
дробовика разброс уже есть — добавки нет), поэтому прежнее «пистолет + веер = 3 снаряда»
сохраняется точь-в-точь. Тик по-прежнему 0 allocs/op, без регресса (см. BENCHMARKS.md).

## Рывок — предсказываемая абилка (итерация 27)

Рывок (dash) — короткое ускорение в сторону движения по действию с кулдауном.
Ключевая сложность: движение **предсказывается клиентом** (общий `Step` зеркалится в
`web/game.js`), поэтому абилка должна укладываться в предсказание, а не только считаться
на сервере.

**Почему input-driven.** Рывок запускается вводом (не пикапом), поэтому клиент
предсказывает его из СВОЕГО ввода тем же кодом, что и WASD, а сервер применяет из того
же ввода — они сходятся без пересылки «серверного буфа» клиенту (в отличие от устойчивого
буста скорости, у которого предсказание было бы дрейфующим — он отложен).

**Состояние в `MoveState`.** Таймеры `dashCD` (до следующего рывка) и `dashT` (остаток
ускорения) живут в `MoveState` (а не в `Player`), потому что их трогает общий `Step` и
зеркалит клиентское предсказание. Оба в секундах, спадают на `dt` каждый шаг, **входят в
`Checksum`** (влияют на будущее движение) и сбрасываются при респауне (замена `MoveState`).

**Провод.** Buttons занят целиком (WASD+огонь+выбор оружия), поэтому действия едут
отдельным **опциональным** байтом `Input.Actions` (бит `ActDash`); старый ввод без байта
декодируется с `actions=0` (обратная совместимость — боты/e2e не ломаются). Сервер гейтит
рывок по своему кулдауну (анти-чит: клиент может слать `ActDash` спамом, но чаще кулдауна
не рванёт).

**Реконсиляция без двойного счёта.** На клиенте таймеры рывка — ЛОКАЛЬНОЕ состояние live-
цикла; реконсиляция их НЕ переигрывает (иначе повторный прогон pending-вводов дважды
списал бы кулдаун). Вместо этого решение «рывок активен в этом кадре» (`dashActive`)
принимается в live-цикле и **сохраняется в очереди неподтверждённых вводов**; реконсиляция
переигрывает движение по сохранённому флагу, воспроизводя ускорение точно, не трогая
кулдаун. Расхождения клиента и сервера у границы кулдауна (float32 против float64) редки и
гасятся обычной коррекцией предсказания. Тик по-прежнему 0 allocs/op.

## Умный ИИ ботов (итерация 28)

Наполнитель комнат (итер. 17) раньше гонял ботов случайным блужданием; теперь у ботов
ИИ: они видят мир из снапшотов, идут к ближайшему врагу по A* вокруг стен и целятся в
него. Границы прежние — **бот остаётся обычным клиентом**: симуляцию/провод не трогает,
только читает снапшоты и шлёт вводы, поэтому весь ИИ живёт в `internal/bot`, а геометрию
стен получает параметром (не завися от `internal/game`).

**Развязка от игры.** `game.Obstacles()` отдаёт read-only снимок раскладки стен (AABB);
`botfill` конвертирует его в `bot.Rect` и строит навигацию. Так `internal/bot` по-прежнему
не импортирует `game` (стрелка та же: `botfill → game/bot`).

**Навигация.** `bot.Nav` — сетка 32×32 (клетка 128) над картой; клетка заблокирована,
если пересекает стену, раздутую на радиус игрока с зазором. `Nav.Path` — A* (8 связностей,
без срезки углов сквозь стены, октальная эвристика, двоичная куча). Сетка строится один
раз и делится (read-only) между всеми ботами. Путь пересчитывается редко (~2 раза/с на
бота), между пересчётами бот рулит к текущей путевой точке — A* не на каждом кадре.

**Конкурентность.** Как и раньше — две клиентские горутины на бота (плюс серверная
сессия): `Brain.Observe` читает снапшоты и публикует снимок мира (`atomic.Pointer[View]`),
`Brain.Drive` на 60 Гц читает снимок и шлёт ввод. Обе завершаются по отмене `botCtx` /
закрытию соединения — владелец и путь завершения те же, что у прежних `Drain`/`Autopilot`.
Простой случайный `Autopilot` оставлен для `cmd/loadtest` (там нужна дешёвая массовость,
а не умный бой).

## King of the Hill (итерация 29)

Режим захвата зоны: в центре арены — фиксированный круглый «холм»; пока его контролирует
одна сторона (стоит внутри без соперников), она копит очки контроля, и победитель матча
определяется по ним, а не по фрагам. Детерминированная симуляция (обход `w.order`, без
rng/time), поэтому в `Checksum` и реплей-безопасна. Совместим и с FFA (сторона = игрок),
и с командным режимом (сторона = команда, итер. 23).

**Состояние.** `Player.HillScore` — очки контроля, копятся в `stepHill` (фаза 5 общего
`Step`, по актуальным позициям, только в активном матче), обнуляются на старте матча —
**в `Checksum`**. Флаг `hillMode` — фиксированный параметр мира (как `teamMode`, через
`SetHillMode` до первого join): в `Checksum` НЕ входит, но пишется в лог реплея (v4).
Геометрия холма (центр/радиус) статична и одинакова во всех мирах, поэтому в `Checksum`
не входит (как `walls`/`pickupSpots`) — в хэш идёт лишь её следствие (`HillScore`).

**Контроль.** `stepHill` собирает живых игроков в зоне и множество их сторон: ровно одна
сторона внутри → она контролирует (каждому её игроку внутри +1); ноль или ≥2 сторон
(пусто/оспаривается) — никто не копит. Победитель (`endMatch`): в FFA — игрок с максимумом
очков (`hillLeader`), в командном — команда с большей суммой (`hillWinningTeam`).

**Провод.** `MsgMatchState` получил флаг `hillMode` (бит1 в байте флагов, рядом с
`teamMode`) и поле `HillScore` в каждой строке табло; снапшот/дельта не тронуты. В hillMode
табло сортируется и победитель считаются по очкам холма. Клиент рисует зону (константы
`SIM.Hill*` зеркалят серверные), подсвечивая контролёра **локально** по игрокам в зоне
(провод «кто держит сейчас» не несёт — клиент выводит сам из позиций), и показывает
очки холма в табло/баннере. Геометрия и радиус синхронны между сервером и клиентом.
