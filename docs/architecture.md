# Архитектура

Документ описывает устройство сервера на текущей итерации и модель
конкурентности, на которой держится весь проект. Обновляется по мере итераций.

## Слои и зависимости

```
                 ┌────────────────────────────────────────────┐
   браузер  ───► │ cmd/server (HTTP/WS gateway, конфиг, pprof) │
   (web/)  WS    └───────────────┬────────────────────────────┘
                                 │  transport.Conn
                     ┌───────────▼───────────┐
                     │        hub            │  менеджер комнат
                     └───────────┬───────────┘
                                 │  *game.Room
                     ┌───────────▼───────────┐
                     │        game           │  симуляция (без сети!)
                     │  room · world · step  │
                     │  clock · session      │
                     └───────────┬───────────┘
                                 │  protocol.* (типы + кодек)
                     ┌───────────▼───────────┐
                     │      protocol         │  данные, без игры и без сети
                     └───────────────────────┘
```

Жёсткие правила границ (проверяются глазами и `go vet`, позже линтером):

- **`protocol`** не импортирует ничего игрового и ничего сетевого. Его можно
  фаззить и бенчмаркать изолированно.
- **`game`** не знает про WebSocket — только `transport.Conn`. Симуляция
  запускается в тестах вообще без сети (`transport.Pipe`, `ManualClock`).
- **`transport`** прячет конкретный стек за интерфейсом `Conn`, чтобы позже
  добавить WebRTC DataChannel, не трогая игру.

## Модель конкурентности

Центральный инвариант: **одна комната = одна горутина**. Игровое состояние
(`World`) не защищается мьютексами, потому что его трогает ровно один код —
game loop комнаты. Всё внешнее заходит в комнату через каналы.

```
                       ┌──────────────── Room.Run (1 горутина) ───────────────┐
   readPump ──input──► │                                                      │
   (на сессию)         │   inbox (chan event) ──► drainInbox ──► World.Step   │
   Join/Leave/State ──►│                                    └──► broadcast ───┼─► out (на сессию)
                       │                                    └──► dropLaggards │
                       └──────────────────────────────────────────────────────┘
                                                                   │
   writePump (на сессию) ◄──────────────────── out (chan []byte) ──┘
```

- **inbox** — единственный вход в комнату. Джойны, покидания, вводы и запросы
  состояния — всё это события `event`, обрабатываемые между тиками. `Input` —
  негарантированное событие: если inbox переполнен, ввод дропается (через ~16 мс
  придёт следующий), лишь бы не блокировать readPump.
- **out** — исходящая очередь сессии. Писать в неё и **закрывать** её имеет право
  только комнатная горутина (правило «закрывает только отправитель»). Очередь
  маленькая: устаревший снапшот бесполезен. При переполнении дропается самый
  старый снапшот; систематическое отставание → дисконнект. Game loop никогда не
  ждёт медленного клиента.

### Владение горутинами

Каждая горутина имеет владельца и явный путь завершения:

| Горутина            | Кто запускает      | Как останавливается                         |
|---------------------|--------------------|---------------------------------------------|
| `Room.Run`          | `hub`              | отмена контекста → доигрывает тик → `Done()` |
| `Session.readPump`  | `Session.Run`      | ошибка чтения / отмена контекста            |
| `Session.writePump` | `Session.Run`      | комната закрывает `out`, или ошибка записи  |
| pprof/HTTP servers  | `main`             | `srv.Shutdown` при graceful shutdown        |

`Session.Run` связывает read- и write-pump: падение любого из направлений
отменяет общий контекст сессии и роняет второе — полусессия бесполезна.

## Жизненный цикл соединения

1. Браузер открывает WS на `/ws`. `transport.Upgrade` даёт `Conn`.
2. Gateway читает первый кадр — это должен быть `Join` (в пределах `JoinTimeout`).
3. `hub.Assign` выдаёт комнату с местом (или создаёт новую).
4. `room.Join` (через inbox) добавляет игрока в мир, создаёт `Session`, ставит в
   очередь `JoinAck` и возвращает сессию.
5. `Session.Run` крутит pumps до дисконнекта или shutdown.

## Graceful shutdown

SIGINT/SIGTERM отменяет базовый контекст в `main`. Дальше по цепочке:
HTTP-сервер перестаёт принимать соединения → комнаты доигрывают текущий тик и
закрывают сессии (закрывая `out`, что завершает writePump) → `hub.Wait`
дожидается остановки всех комнат. Тик никогда не прерывается на полпути —
мир не остаётся в полупросчитанном состоянии.

## Детерминизм

Симуляция обязана быть детерминированной — это фундамент реплеев и клиентского
предсказания. Поэтому внутри `game`:

- обход игроков — только по отсортированному срезу `order`, не по map;
- случайность — только через `World.rng` (seeded PCG), не через глобальный `rand`;
- время — только через `Clock`, не через `time.Now()` напрямую в логике.

Тест `TestWorldDeterminism` гоняет два мира с одним seed и одной лентой вводов и
сверяет `World.Checksum()` побайтово. Подробнее — в [testing.md](testing.md).

## Частота снапшотов (итерация 2)

Тикрейт 30 Гц, но снапшоты уходят на 20 Гц — реже, чем считается мир. 20 не
делит 30 нацело, поэтому используется делитель частоты по Брезенхэму
(`rateDivider`): накопитель растёт на `SnapshotRate` каждый тик и, перевалив за
`TickRate`, выпускает снапшот и вычитает `TickRate`. Это даёт ровно 2 снапшота на
3 тика, равномерно. Разрыв между сервером и клиентом скрывает клиентская
интерполяция: клиент буферизует снапшоты и рендерит мир на 100 мс в прошлом,
интерполируя позиции между двумя соседними снапшотами на серверной шкале времени.

## Lag compensation (итерация 5)

Клиент из-за интерполяции (рендер на 100 мс в прошлом) и RTT видит цели в прошлом.
Чтобы попадания считались по тому, что игрок реально видел, сервер перематывает
цели во времени. Каждый игрок держит кольцо `posHist` — позиции за последние
`historyLen` тиков, записываемые каждый тик под меткой `Snapshot.tick`. В каждом
вводе клиент шлёт `ViewTick` — серверный тик, к которому он интерполировал. При
выстреле сервер фиксирует на снаряде постоянный сдвиг `rewind = clamp(now −
ViewTick, 0, maxRewindTicks)` и на каждом тике полёта проверяет попадание против
позиции цели из истории на `rewind` тиков назад — снаряд и «отмотанная» цель идут
в локстепе, воспроизводя ровно то, что видел стрелок. Кламп окна — анти-чит:
отмотать цель произвольно далеко нельзя. Кольцо истории и `rewind` входят в
`Checksum` — это будущее состояние, от которого зависит следующий hit-тест.

## Что впереди (по итерациям)

Итерации 3–5 сделаны: бинарный кодек (`protocol`, zero-alloc), client prediction +
reconciliation (общий `Step` зеркалится на клиенте), бой (снаряды, урон,
смерть/респаун, reliable-события) и lag compensation. Осталось:

- **6** — spatial hash grid, interest management, дельты, нагрузка 200 ботов.
